# API の読み方

## 辿り方

ルート定義 → ハンドラ → サービス → リポジトリ。この 4 段を辿って初めて
「この API がどのテーブルを触るか」が分かる。ルート定義だけ見て書かない。

## 探す場所

| 形 | 典型的な場所 |
| --- | --- |
| 定義ベース | `routes/` `controllers/` `endpoints/` |
| ファイルベース | `app/**/route.ts` `pages/api/**` |
| デコレータベース | `@Controller` `@Get` などの付いたクラス |
| GraphQL | `resolvers/` `*.graphql` |
| 自動生成 | Strapi のような CMS。`references/stacks/` を見る |

## 取るもの

- **Validation** — スキーマ定義（zod / class-validator / DTO / JSON Schema）から取る。
  無ければハンドラ内の分岐から拾い、**出所のファイルを明記する**
- **Status Code** — 実装に現れるものだけ。フレームワーク既定の暗黙値は「既定」と明記
- **認証・認可** — ミドルウェアやデコレータの適用範囲から判定する。
  認可は「誰のデータを触れるか」まで書く（リクエストボディの id を使うのか、トークンから取るのか）
- **関連テーブル** — 辿った先のリポジトリ層が触るテーブル。CRUD をつける
- **トランザクションの境界** — 部分的な失敗が起きうるかどうか。障害調査でここが効く

## 分量の判断

エンドポイントが 30 本を超える場合、詳細章は主要なものに絞ってよい。
ただし**一覧表は全エンドポイントを載せる。** 一覧から漏れると存在自体が見えなくなる。

「主要」の判断はコードから行う。画面から呼ばれている、他の API から呼ばれている、
テーブルを更新する、のいずれかに当たるものを優先する。

## 判定できないとき

- レスポンスの型が動的で読めない → 「未確認」と書き、読めた範囲だけ書く
- ミドルウェアの適用範囲が動的 → 認証欄を「未確認」にする
- 外部から呼ばれる想定か内部専用か分からない → 未確認一覧へ
