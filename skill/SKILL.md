# design-doc

対象プロジェクトのソースコードから、**人間が読んで理解できる機能単位の設計書**を作る。

生成する設計書は 3 つの用途を同時に満たす必要がある。

1. **チームメンバーの仕様把握** — 初見の人がこのページだけで機能の全体像と細部を把握できる
2. **テスト仕様書作成の元ネタ** — 「〜という場合は〜になる」という分岐条件・エラーコード・具体的な数値が、既存 docs の要約レベルではなく**実装コードを読んだ上での粒度**で書かれている
3. **客への提案資料** — 非エンジニアが読んでも機能の意図が分かる説明も併記する

削って後悔するより、書きすぎて指摘を受ける方向に倒す。

## モード

| モード | 状態 | 内容 |
| --- | --- | --- |
| `init` | 実装済み | 機能を切り出し、全設計書を生成し、Notion へ反映する |
| `sync` | **未実装** | 定期実行でソース変更に追随する。init の実物を見てから設計する |
| `focus` | **未実装** | 1 機能だけ作り直す。当面は init の再実行で代用する |

`sync` / `focus` を求められたら「未実装。init の再実行で対応する」と伝える。勝手に実装しない。

```
/design-doc init <path...>       例: /design-doc init ~/project/sa-repo ~/project/app
```

一度 init 済みの案件で init を再実行した場合は**境界の見直しモード**になる。既存の機能一覧と未分類を並べて提示し、統合・分割・新規追加を人間が決める。変わらない機能は再生成しない。

## 00 セットアップ

AskUserQuestion で 3 つ聞く。**推測で決めない。**

1. **案件名** — 作業ディレクトリ名になる。英数字とハイフンに正規化する。既存と衝突したら「境界の見直しモードに入るか、別名にするか」を聞く
2. **Notion の親ページ** — URL を受け取る
3. **Notion の階層の形** — 「親 > ドメイン > 機能」か「親 > 機能」か

作業ディレクトリを作る。

```
~/.claude/design-docs/<案件名>/
├── config.json     対象リポのパス / Notion 親ページ / 階層の形
├── progress.json   機能ごとの状態
├── style.md        この案件の型（08 で育つ）
└── features/
```

`progress.json` の状態は 4 つ。`未生成` / `生成済み未承認` / `承認済み` / `保留`。

## 01 読み方を探す

各リポジトリを探索し、**どこに何が書いてあるか**を特定する。スタック別の共通レシピは持たない。プロジェクトごとに構造が違うので毎回ゼロから探す。

探すもの:

- ルート定義 / 画面ルーティング / バッチ定義 / Webhook ハンドラ / キュー・イベント消費
- 定数の置き場 / エラー定義の置き場 / DB スキーマ

manifest（`package.json`, `pubspec.yaml`, `go.mod` など）から言語とフレームワークを掴み、そこから定義の在り処を辿る。**この結果は人間に見せない。** 次の 02 の材料として使うだけ。

## 02 入口を列挙

利用者から見える入口をすべて列挙する。ここが機能の起点になる。

- API ルート（method + path）
- 画面ルート
- バッチジョブ
- Webhook ハンドラ
- キュー・イベント消費

入口はコード上に定義として存在するので、パターンが分かれば機械的に列挙できる。**ただし独自構造のものは取りこぼしうる。** それは 04 で人間に気づいてもらう。

## 03 機能クラスタを作る

1. 入口をパスの意味的なまとまりでグループにする（`/auth/registration/*` と画面の `/registration/*` は同じ機能）
2. **フロントとバックは `method + path` で結合する。** 機能名は一致しないので名前では結ばない。フロントの API クライアント層が持つエンドポイントを突き合わせのキーにする
3. 参照を辿って担当ファイル集合を確定する（route → handler → service → repository → schema / screen → controller → data source）
4. **入口を持たないコード**（共通ライブラリ・ユーティリティ）は、参照元の機能に含める。複数の機能から呼ばれるものは重複して入れてよい
5. 機能名はパス接頭辞から起こす。人間が改名できる

## 04 機能一覧を提示 ── 人間ゲート ①

AskUserQuestion ではなく、一覧を提示して自由に指示をもらう。出すもの:

- 機能名と担当パス（リポジトリごとに分けて）
- **どの機能にも入らなかったディレクトリ** — 拾い漏れに人間が気づける唯一の機械的な手段。必ず出す

人間が 統合 / 分割 / 改名 / 追加 を指示する。**ここで決まった境界と名前が以後ずっと基準になる。**

確定したら `progress.json` に全機能を `未生成` で登録する。

## 05〜08 を 1 機能ずつ繰り返す

**まとめて全機能を生成しない。** 1 本書いて人間に見せ、指摘を型に反映してから次へ進む。そうしないと同じ指摘を全機能ぶん受けることになる。

### 05 生成

`template.md`（章の定義）に従って書く。`style.md` があれば併用する。**矛盾したら `template.md` が勝つ。**

- 言語は日本語固定
- 実装コードを実際に開いて読む。既存 docs の要約で済ませない。docs の数値は古いことがあるので**実装値で上書きする**
- **テーブル 10 以上 または 外部連携あり**なら、親ページ＋サブページに分割する。分割の切れ目は章単位

出力先は `features/<機能名>.md`（分割時は `features/<機能名>/<章>.md`）。

### 06 機械チェック

```bash
python3 ~/.claude/skills/design-doc/scripts/verify.py \
  --doc <生成した md> --repo <リポパス> [--repo <リポパス>...]
```

設計書に書いた識別子がソースに実在するかを照合する。対象はエンドポイント / errorType / テーブル名。**定数の値は対象外**（設計書「30 分」・コード `1800` のような表記揺れで誤検知が出るため）。

- 不一致 → 出力された指摘を材料に**再生成する。リトライは 1 回だけ**
- 2 回目も不一致 → `progress.json` を `保留` にして次の機能へ進む。理由を記録する

### 07 機密検出

```bash
python3 ~/.claude/skills/design-doc/scripts/secrets.py --doc <生成した md>
```

設計書に載ってはいけない情報が混ざっていないか調べる。認証情報・鍵 / 個人情報（実データ）/ 取引先名・契約情報。

**検出したらリトライせず常に人間に見せる。** 誤検知（仕様説明中の「パスワードリセット」やテスト用ダミーメール）が出るので、伏せ字にする判断を機械にさせない。人間が「誤検知」と言えばそのまま進み、「本物」と言えば該当箇所を落として再生成する。

### 08 人間が読む ── 人間ゲート ②

生成した md のパスと内容を提示する。**この時点では Notion に上げない。**

人間が見るのは**分類の仕方・章構成・読みやすさ**。内容の正しさを全部検証させるのではない（そこは 06 と、後から気づいたときの直しで担保する）。

- 指摘があった → **その指摘をルールとして `style.md` に書く**。文章そのものは保護しない。書いたら 05 へ戻って生成し直す
- 承認された → `progress.json` を `承認済み` にして次の機能へ

`style.md` に書く粒度の例:

```markdown
- 画面遷移図は画面を主語にする。API 名を主語にしない（非エンジニアが読むため）
- エラー一覧は errorType 単位。1 行に複数の errorType を混ぜない
- フロー図は判定ノードごとに分ける。1 枚に詰め込まない
```

## 09 Notion へ一括反映

**全機能が `承認済み` になってから**まとめて反映する。中断中に Notion が中途半端な状態にならないため。

`保留` が残っている場合は、保留分を除いて反映するか止めるかを人間に確認する。

1. `mcp__notion__notion-fetch` で親ページを取得し、既存の子ページを確認する
2. 00 で決めた階層に配置する。ドメイン階層を作る場合、ドメインページの本文は 1〜2 行の説明のみ
3. 既存ページがあれば `mcp__notion__notion-update-page`（`replace_content`）で上書きする。新旧で機能の切り分けが割れた場合は新規作成し、対応が失われた旧ページを削除する。**削除は必ず一覧を提示して人間の確認を取ってから**
4. 反映に失敗したら人間が手動でアップロードする。ローカル md のパスを伝える

### Notion 向け書式制約

- 見出しは `#`〜`###` まで（Notion のヘッダーは H1〜H3 のみ）
- フロー図・画面遷移図は Mermaid（```mermaid の `flowchart TD`）。Notion はネイティブに描画する。ASCII 箱型図は日本語混じりだと文字幅が揃わず崩れるので使わない
- 表示直後に崩れて見えることがある。**ページを再読み込みして確認する。** すぐに ASCII 図へ後退させない
- テーブルは 4 列以内が原則。ただし ○ / × のような 1 文字セルで構成される表（CRUD 表など）は例外として列数を増やしてよい
- 相対パス・ファイルパスはインラインコードで書く（自動リンク化を避けるため）
- ページ冒頭にメタ情報の callout は付けない。タイトルの次はいきなり「## 1. 概要」から始める

## 10 反映を検証

反映したページを `mcp__notion__notion-fetch` で読み返し、ローカル md と照合する。

- 見出しの数
- Mermaid ブロックの数
- テーブルの数

不一致なら再反映する。**「反映した」で終わらせない。** 過去に反映済みのつもりで実ページが存在しなかった事故がある。

検証を通った機能だけ、`progress.json` に Notion ページ ID と反映日を記録する。

## 書かないこと

- 推測で埋めた仕様。不明な点は「未確認」と明記して埋めない
- 検討の経緯や却下案のうち、既存 docs にもコードコメントにも記録が無いもの。ないものを創作しない
- 対象外の機能への言及。ただし呼び出す関連機能は「対象外」ではなく本文で扱う対象

## このスキルの限界（人間に伝えるべきこと）

- **漏れゼロは機械で保証できない。** API・画面ルートは確実に列挙できるが、バッチや Webhook は書き方がプロジェクト次第で独自構造なら取りこぼしうる
- **機械チェックは作文しか検出できない。** 「実在しないエンドポイントを書いた」は防げるが、「分岐条件の説明が実装と違う」「書かれていない分岐がある」は検出できない
- **機密検出は誤検知が出る。** だから自動で伏せ字にせず、常に人間の判断に回す
