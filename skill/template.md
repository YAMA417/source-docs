# design-doc テンプレート

章の定義と書き方。これが全案件共通の正本で、案件ごとの調整は `style.md` に書く。
**`style.md` と矛盾したらこのファイルが勝つ。**

セクションは省略しない。情報が薄いセクションがあれば「省く」のではなく「なぜ薄いか（未確認 / 該当なし）」を明記する。

対象にそのスタックが含まれない章は出さない（バックエンドしかない機能に画面遷移図を書かない）。

---

## ファイルの先頭

```markdown
# <機能名>
```

メタ情報（対象ドメイン・最終更新日・参照ファイル一覧）の callout は付けない。更新のたびに腐るわりに読者価値が低い。タイトルの直後にいきなり「## 1. 概要」から始める。

## 1. 概要

何のための機能か。対象範囲。**非エンジニアが読んでも分かる説明**にする。

## 2. 業務フロー図（Mermaid・必須）

Mermaid の `flowchart TD` を使う。ASCII 箱型図は日本語混じりだと文字幅が揃わず崩れるので使わない。Notion は Mermaid コードブロックをネイティブに描画する。

```markdown
​```mermaid
flowchart TD
    A["<起点となるイベント・API 呼び出し>"] --> B{"<判定内容>"}
    B -->|<分岐A>| C["<処理・結果>"]
    B -->|<分岐B>| D["<処理・結果>"]
​```
```

- 判定ノードは `{"..."}`（ひし形）、処理・結果ノードは `["..."]`（四角）
- ノード内の改行は `<br>`（`\n` は使えない）。括弧などを含むラベルはダブルクォートで囲む
- **判定・分岐が無い単純な直列処理だけの図は疑う。** 実装を読めばどこかに分岐（エラー処理・条件分岐・ロールバック）があるはず
- 意思決定ポイントが複数あるなら、1 枚に詰め込まず図を分ける
- 図の直後に、図だけでは拾えない細部（入力検証・業務ルール・失敗時の挙動）を箇条書きで補足する
- **主フローに強く影響する隣接処理は、実行主体が別でも省略しない**（例: 管理画面からのアカウント無効化がログインを止める）

## 3. 画面遷移図（画面がある場合は必須・Mermaid）

**画面が主語。API 呼び出しを主語にしない。** 読者に非エンジニアが含まれる。「EmailRegistration (POST /auth/registration/session)」のような書き方は各画面の説明の末尾に小さく添えるだけにして、図の主役は「利用者が何を見て、何を押すと次に進むか」にする。

```markdown
​```mermaid
flowchart TD
    A["①<画面の案内文><br>【<ボタン文言>】"] --> B["②<次画面の案内文>"]
​```
```

- **遷移の順序を推測で描かない。** ルーティング定義が正本。ネストの親子関係がそのまま遷移を表す
- **表示文言・ボタン文言は実際の文言リソースから拾う。** 画面ファイル自体はキー参照しか持たないことが多い
- **どの操作が API 呼び出しの引き金かは、該当画面のコントローラを実際に読んで確認する。**「〜と推定」で済ませない
- 画面数と API 呼び出し回数が一致しない場合（複数画面の入力を 1 回にまとめている等）、それ自体を明記する

## 4. 対象テーブルと CRUD 表（必須）

新規テーブル・スキーマ変更がある場合は、CRUD 表の前に「対象テーブル」小節を置く。無ければ「スキーマ変更なし」と明記する。

フローの各ステップがどのテーブルに何をするかを一覧化する。テスト担当者はこの表から DB 検証項目を起こすので、**実装コード（ORM 呼び出し）を実際に読んで拾う。** ドキュメントやコメントの記述だけで済ませない。

DB 区分は見出しで分けず列にする。

```markdown
| DB | テーブル | C | R | U | D | 備考 |
| --- | --- | --- | --- | --- | --- | --- |
| <区分> | <テーブル名> | ○/— | ○/— | ○/— | ○/— | <いつ・何のために・どの列か> |
```

該当なしは `—`。C/R/U/D は 1 文字セルなので 4 列制限の例外として扱う。詳細は備考列にまとめる。

## 5. 業務ルール・制約一覧

数値・条件を表で。**既存 docs の数値を鵜呑みにせず、定数定義の実装値で裏取りする。** docs と実装がズレていたらそれ自体を明記する（地雷情報として価値が高い）。

```markdown
| 項目 | 値 | 出典 |
| --- | --- | --- |
```

## 6. エラーケース一覧

テスト仕様書の元ネタになる粒度で書く。発生条件・ステータス・errorType を、**サービス層の分岐とハンドラ層のエラーマッピングの両方**から拾う。既存 docs に書かれていない分岐がほぼ必ずある。

```markdown
| 発生条件 | ステータス | errorType |
| --- | --- | --- |
```

errorType はインラインコードで書く。機械チェック（`scripts/verify.py`）がこの列を見て実在確認する。

## 7. 設計判断

なぜこの設計にしたか。情報源の優先順位:

1. コード内コメントの WHY（サービス層に最も多い）
2. 既存 docs 本文中の WHY 記述
3. 要件定義書の「制約・前提」「スコープ外」「レビュー」セクション

```markdown
- **<判断>。** 理由: <なぜ>（出典: `<path>`）
```

記録が見つからなければ「記録なし」と明記する。**無理に推測で埋めない。**

**ドキュメントとコードの矛盾を見つけたら、ここか「ドキュメントの罠」小節に書く。** 例: docs が「ASCII 文字のみ」と書いているが実装のバリデーションにその制約が無い、といった食い違いは読者への警告として価値が高い。

## 8. 実装構造

リポジトリごとに分けて、ディレクトリツリーまたは表で書く。

## 9. 関連リンク

元にした docs・要件定義書へのリンク（相対パスをインラインコードで）。

## ページ分割

**テーブル 10 以上 または 外部連携あり**なら、親ページ＋サブページに分ける。

- 親ページ: 1. 概要 / 4. 対象テーブルと CRUD 表 / 5. 業務ルール / 6. エラーケース / 9. 関連リンク
- サブページ: 2. 業務フロー図 / 3. 画面遷移図 / 7. 設計判断 / 8. 実装構造

親ページの先頭にサブページへのリンク一覧を置く。

## 深さのセルフチェック

書き終えたら自問する。詰まったら、その部分の調査が足りていない。

- CRUD 表を見て、テスト担当者が「このテーブルにこの状態のレコードがあるとき」というテストケースの前提を組み立てられるか
- エラーケース一覧を見て、境界値・異常系のテストケースを過不足なく洗い出せるか
- 業務フロー図を見て、非エンジニアが「何が起きて何が起きないか」を説明できるか
- 設計判断を見て、「なぜこうしなかったのか」への回答がどこかにあるか
- 画面がある機能なら、画面遷移図が実際のルーティング定義に基づいているか（コントローラ内の遷移呼び出しの推測で描いていないか）
- 実行主体が別（管理画面・バッチ）でも利用者の体験に直結する処理を「関連機能だから」で薄くしていないか
