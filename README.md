# design-doc スキル

任意のリポジトリ（複数可）のソースコードを読み込んで、機能単位の設計書を生成する Claude Code スキル。

生成する設計書は 3 つの用途を同時に満たすことを狙う。

1. **チームメンバーの仕様把握** — 初見の人がそのページだけで機能の全体像と細部を把握できる
2. **テスト仕様書作成の元ネタ** — 分岐条件・エラーコード・具体的な数値が、既存 docs の要約ではなく実装コードを読んだ粒度で書かれている
3. **客への提案資料** — 非エンジニアが読んでも機能の意図が分かる説明を併記する

---

## 構成

```
skill/
├── SKILL.md          スキル本体（00〜10 のワークフロー定義）
├── template.md       章の定義。全案件共通の正本
└── scripts/
    ├── verify.py     生成した設計書の識別子がソースに実在するか照合
    └── secrets.py    設計書に機密情報が混ざっていないか検査

notes/                再検討用の材料（GitHub には上げない想定）
├── 01_旧設計メモ_dr-design-doc.md   汎用化する前の案件専用版の設計
├── 02_運用知見_style.md             実行して分かった Notion 反映の落とし穴
└── 03_config例.json                 作業ディレクトリの config 実例
```

## インストール

`~/.claude/skills/design-doc/` に `skill/` の中身を置く。

```
~/.claude/skills/design-doc/
├── SKILL.md
├── template.md
└── scripts/
```

## 使い方

```
/design-doc init <path...>
```

例: `/design-doc init ~/project/backend ~/project/mobile-app`

フロントとバックが別リポジトリでも同時に渡せる。`method + path` で突き合わせて 1 機能として扱う。

### ワークフロー

| 段階 | 内容 | 人間の関与 |
| --- | --- | --- |
| 00 | 案件名 / Notion 親ページ / 階層の形を確認 | 必須（AskUserQuestion） |
| 01 | リポジトリの構造を探索し、どこに何が書いてあるかを特定 | なし |
| 02 | 利用者から見える入口（API ルート / 画面 / バッチ / Webhook）を列挙 | なし |
| 03 | 入口をパスの意味的なまとまりで機能クラスタにする | なし |
| 04 | 機能一覧と未分類ディレクトリを提示 | **ゲート①** 境界と名前を確定 |
| 05 | 1 機能ぶんの設計書を生成 | なし |
| 06 | `verify.py` で識別子の実在を照合 | なし（不一致なら 1 回だけ再生成） |
| 07 | `secrets.py` で機密検出 | 検出したら必ず人間へ |
| 08 | 生成物を提示 | **ゲート②** 指摘を `style.md` に反映して 05 へ戻る |
| 09 | 全機能が承認済みになってから Notion へ一括反映 | なし |
| 10 | 反映したページを読み返してローカルと照合 | なし |

`sync`（定期実行でソース変更に追随）と `focus`（1 機能だけ作り直す）は未実装。

## 生成される設計書の構成

テーブル 10 以上または外部連携ありなら、親ページ＋サブページに分割する。

```
<機能名>/
├── index.md        概要 / 用語 / 対象テーブルと CRUD 表 / 業務ルール / エラーケース / 関連リンク
├── 業務フロー.md    Mermaid のフローチャート
├── 画面遷移.md      画面を主語にした遷移図 + 実際の表示文言
├── 設計判断.md      なぜこの設計にしたか（記録がないものは「記録なし」と明記）
└── 実装構造.md      ファイル配置と責務
```

## 実行してわかった課題（再検討の材料）

2026-09-04 に実案件（バックエンド Monorepo + Flutter アプリの 2 リポジトリ）へ適用した結果。

### スキル本体に足りていないもの

1. **Notion 反映時の変換規則が書かれていない。** Markdown テーブルは Notion 形式（`<table header-row="true">` + `<tr>` / `<td>`）へ変換が必要だが、SKILL.md には記載がない。変換スクリプトを同梱すべき
2. **ファイル名の自動リンク化。** `requirements.md` のように拡張子付きの語を裸で書くと `[requirements.md](http://requirements.md)` にされる。「相対パスはインラインコード」という規則は書いてあるが、ファイル名単体も対象だと明記されていない
3. **1 ページあたりの content 上限。** 30KB 程度を超えると送信が通らない。create → update(insert_content) で分割する必要がある。SKILL.md に上限の記載なし
4. **日本語のエスケープミスは送信時に検出できない。** 「掃除→掎除」「恒久→恆久」のような 1 文字の取り違えが実際に 4 件発生した。10（反映を検証）で fetch して照合しないと気づけない。この検証は現状「見出し数 / Mermaid 数 / テーブル数」しか照合対象に挙げていないので、本文の文字列比較も加えるべき
5. **HTML 版の併産が規定にない。** 今回は非エンジニア向けにインライン SVG のフローチャート入り HTML を別途作ったが、これはスキル外の判断だった。オプションとして規定するか、別スキルへ委譲するかを決める必要がある

### ワークフローの運用で気づいたこと

6. **04 の「未分類ディレクトリを必ず出す」が、スコープ限定の依頼だと機能しない。** 「◯◯の設計書を作って」と機能を指定された場合、全リポジトリの未分類を出しても大半がノイズになる。「判断が割れるもの」を出す形へ読み替えたが、スキル側にその分岐を書いておくべき
7. **06 の機械チェックが弱い。** エンドポイント / errorType / テーブル名の実在確認だけなので、「分岐条件の説明が実装と違う」「書かれていない分岐がある」は検出できない。この限界は SKILL.md に明記済みだが、テーブル名の単複（`prize_order_shopify_order` を複数形で書いた）のような誤りは実際に検出できて有用だった
8. **既存ドキュメントとの矛盾を洗い出す価値が高い。** 実案件では要件定義書の本文と実装値が 3 箇所食い違っており（保持期間 30 日 vs 180 日など）、これを「ドキュメントとコードの矛盾」章として独立させたことが読み手に一番喜ばれた部分だった。template.md では 7 章の一部として扱っているが、独立章に格上げしてもよい

### スキル本体の汎用性

9. `SKILL.md` 29 行目の使用例が個人環境のパス（`~/project/sa-repo ~/project/app`）になっている。公開前に汎用例へ差し替える
10. `notes/` の中身は案件固有（Notion のページ構成・ドメイン名）。公開リポジトリには含めない
