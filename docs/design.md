# source-docs 設計

2026-09-05 承認。既存の design-doc スキルを置き換える。

図とサンプルは同じディレクトリの HTML にある。

- `design-overview.html` — アーキテクチャ図・ワークフロー図・12 項目の設計
- `output-sample.html` — 生成される 5 資料の書式サンプル（架空のオンライン書店が題材）

---

## 目的

既存プロジェクトのソースコードを読み、初見の開発者がシステム構造を理解するための技術資料を生成する。

想定する読み手は、新しく参画した開発者・既存機能を改修する開発者・全体を俯瞰したい開発者。コードの羅列や要約ではなく、資料を読むことで構造が分かる状態を目指す。

**最重要要件** — ソースコードから確認できない情報を事実として書かない。

## 確定事項

| 論点 | 決定 |
| --- | --- |
| スキルの位置 | design-doc を置き換える。機能単位 + Notion 反映という旧構成は引き継がない |
| 解析方式 | ハイブリッド。機械的に取れるものはスクリプト、意味付けは Claude |
| 対応技術 | 汎用手順を本体に置き、フレームワーク固有の読み方は `references/stacks/` へ分離 |
| 検証対象 | poke-dex-battle / kids-play-monorepo / oshinote の 3 プロジェクト |
| 出力形式 | Markdown が正本。HTML は Markdown から変換。HTML は複数ページ + index |
| Notion 反映 | このスキルに含めない。md を Notion へ変換する別スキルとして後日開発 |
| 中間表現 | JSON / YAML の中間表現ファイルは作らない |
| 人間の補足編集 | MVP 対象外 |

## アーキテクチャ

```
ソースコード ─┐
              ├→ inventory.py（候補列挙・決定的）─→ Claude が実装を読む ─→ Markdown（正本）─┬→ md2html.py → HTML
manifest / 設定 ┘   スタック判定                        意味付け・関連付け                    └→（将来）別スキル → Notion
```

`inventory.py` の出力は探索の足場であり、資料の生成元ではない。生成元は Claude が読んだ実装そのもの。生成後に捨ててよい。

「解析と表現の分離」は Markdown を正本に固定することで担保する。出力形式を足すときに触るのは変換器だけで、解析側は変わらない。

### ハイブリッドの分担

- **スクリプト** — ファイル一覧、ルート定義らしき行の抽出、マイグレーション / スキーマファイルの発見、依存関係の読み取り、件数の集計
- **Claude** — 候補が本物の入口か、テーブルが何のために存在するか、画面がどの API を呼ぶか、遷移がどこへ向かうか

スクリプトが「探すべき場所」を絞り、Claude はそこだけを深く読む。全ファイルを Claude に読ませないことが、大規模リポジトリで破綻しない条件。

## コマンド

```
/source-docs [target] [--format md|html|both] [--out <dir>] [--repo <path>]
```

- `target` 省略 = `all`。取れる値は `all` / `overview` / `db` / `api` / `screens` / `integrations`
- `--format` 省略 = `md`
- `--out` 省略 = `docs/system`
- `--repo` 省略 = カレントディレクトリ。複数リポジトリは `--repo` を繰り返す

ER 図とビュー章は `db` に、画面遷移図と画面-API-DB 関連は `screens` に含む。図だけ単独で作り直す用途がないため、別ターゲットにしない。

## ワークフロー

人間が止める場所は 2 か所。

| # | 段階 | 内容 |
| --- | --- | --- |
| 00 | スタック判定 | manifest と設定ファイルから、フロント / バック / ORM / DB / Router / API フレームワークを判定。該当する `references/stacks/` があれば読む |
| 01 | 列挙 | `inventory.py` で、ルート候補・スキーマ候補・画面候補と件数を出す |
| — | **ゲート 1** | 判定結果と件数を提示し、人間が対象範囲を確定する。判定を外していればここで直る |
| 02 | 1 資料目 | 実装を読んで md を書き、`verify.py` で識別子の実在を照合する |
| — | **ゲート 2** | 1 本目を人間が読む。見るのは章構成・粒度・読みやすさ。指摘は規則として記録し以降に効かせる |
| 03 | 残り資料 | 同じ手順で残りを生成・照合する |
| 04 | HTML 変換 | `--format` に html があれば `md2html.py` を実行 |
| 05 | 完了報告 | 生成ファイル一覧と未確認一覧を出す。`secrets.py` の検出は人間に回す |

全資料をまとめて生成してから見せない。1 本目で型を決めないと、同じ指摘を 8 本ぶん受けることになる（旧 design-doc で実際に起きた）。

## 生成する資料（8 本）

| ファイル | 内容 |
| --- | --- |
| `overview.md` | システム概要 |
| `database.md` | DB 定義（スキーマ一覧・テーブル定義・Enum・ER 図・ビュー・未確認一覧） |
| `api.md` | API 仕様（共通仕様・エンドポイント一覧・詳細・未確認一覧） |
| `screens.md` | 画面一覧・画面遷移図・画面詳細・画面-API-DB 関連・未確認一覧 |
| `integrations.md` | 外部連携（連携先一覧・送信・受信・認証情報の所在・障害時の挙動・未確認一覧） |

ER 図は `database.md` の 1 章、画面遷移図と画面-API-DB 関連は `screens.md` の各 1 章。要件の 7 資料に外部連携を加えて 8 本。

書式の詳細は `output-sample.html` を正とする。

## ソース解析

### DB

優先順位を固定する。**マイグレーション / スキーマ定義 > ORM のモデル定義 > 実行時のクエリ**。上位が存在するならそれを正とする。

- 取得: テーブル / カラム / 型 / PK / FK / NULL 可否 / Default / Index / Enum / Relation
- スキーマが複数ある場合はスキーマ一覧の章を置き、テーブル名を常にスキーマ修飾で書く。**単一スキーマなら章も修飾も省く**
- スキーマごとに管理主体（自リポジトリ / 外部サービス / 手動）を記録する
- テーブル用途はコードから読む。命名だけで書かない。読めなければ未確認
- ビュー・マテビューは ER 図に入れず独立章へ。更新のタイミングと、利用者に見える経路があるかを書く

### API

- ルート定義から入り、ハンドラ → サービス → リポジトリと参照を辿る
- Validation はスキーマ定義から取る。無ければハンドラ内の分岐から拾い、出所を明記する
- Status Code は実装に現れるものだけ。フレームワーク既定の暗黙値は「既定」と明記する
- 関連テーブルは CRUD で示す。ここが画面-API-DB 関連表の接続点になる

### 画面

- ルータ定義（ファイルベースならディレクトリ構造）から画面を列挙する
- 遷移は `navigate` / `push` / `Link` / `redirect` から取る。条件付き遷移は条件も記録する
- 画面遷移図は Mermaid の `flowchart`。**画面を主語にする**。ノードに画面名と Route を両方入れる。エラー・条件付きの遷移は破線。12 ノードを超えたらフロー単位で分ける

### 外部連携

- 方向で章を分ける（送信 / 受信）。障害の切り分けが方向単位で行われるため
- 送信は**タイミング・タイムアウト・リトライ・失敗時の挙動**を 4 点セットで拾う
- 受信は署名検証の方法と**冪等性の担保**を拾う
- 認証情報は環境変数名と読み出し箇所だけ。値は書かない
- 設定だけ残って呼び出しが無い連携先も一覧に載せ、未確認にする

## 不明情報の扱い

確度をメタデータとして持たず、本文の書式として持つ。

- **根拠** — 各行に「実装ファイル」欄を持つ。ファイル単位まで。クラス名・関数名は追わない
- **判定できなかったもの** — 該当欄に「未確認」と書き、資料末尾に未確認一覧の章を置く。「調べた範囲」まで書く
- **推測** — 原則書かない。書く場合は「推測」と明示し、根拠にした箇所を併記する
- **機械照合** — `verify.py` がエンドポイント / テーブル名 / errorType の実在を照合。不一致は 1 回だけ再生成し、2 回目も不一致なら未確認として残す

## セキュリティ

このスキルは**他人のリポジトリを読む。** 前提として次を守る。

### 読まない

`scripts/_secure.py` が判定し、`inventory.py` と `verify.py` が適用する。
SKILL.md にも同じ規則を書き、Claude が自分で Read / Grep するときも守らせる。

- 環境変数の実ファイル（`.env` / `.env.local` / `.env.production`）
- 鍵そのもの（`*.pem` / `*.key` / `*.p12` / `*.jks` / `id_rsa`）
- 認証情報ファイル（`credentials.json` / `service-account.json` / `.npmrc` / `.netrc` / `terraform.tfvars`）
- ディレクトリごと（`.ssh/` / `.aws/` / `.gnupg/` / `.kube/` / `credentials/` / `secrets/`）
- **シンボリックリンク。** 名前が `schema.ts` でもリンク先は分からない

例外は `.env.example` などのテンプレートのみ。外部連携の変数名を知るために読み、
**変数名しか見ない。**

### 書き出さない

- 機密検出（`secrets.py`）を**各資料の生成直後に走らせる。** 完了報告時の 1 回では、
  書いてから気づくまでが遠い
- 検出値は**既定で伏せる。** ターミナルやログに機密が残らないため。
  中身を見るときは `--reveal` を明示する
- **検出しても自動で伏せ字にしない。** 誤検知が出るので判断は人間に回す

### 生成 HTML

`md2html.py` の出力はブラウザで開かれる。元になるのは他人のリポジトリの文字列なので、
無検査で HTML に入れない。

- リンクの `javascript:` / `data:` / `vbscript:` スキームを落とし、`href` を属性としてエスケープする
- Mermaid は `securityLevel: strict`。あわせて図のラベルで HTML タグを使わない
- 出力先が `.git` / `node_modules` を含む、またはホーム直下なら拒否する
- 既存ファイルの上書きは標準エラーに出す。黙って上書きしない

### 外部送信

**しない。** ネットワークへ出す処理は同梱スクリプトに無く、依存も標準ライブラリだけなので、
外部パッケージ経由の送信経路も無い。

### 防げないこと

- 機密検出は誤検知も見落としもある。パターンに無い形式のトークンは検出できない
- 除外リストは名前で判定する。変わった名前のファイルに秘密が入っていれば読んでしまう
- **公開前に人間が読む必要がある。** 社外へ出す資料は特に

## コンテキスト管理

1. **スクリプトが先に絞る** — `inventory.py` が候補を出し、Claude はその周辺だけを開く
2. **資料ごとに実行を分けられる** — `target` を引数に取る理由
3. **1 資料の中でも分割する** — ゲート 1 で件数が分かるので、多い場合はディレクトリ単位でサブエージェントに分けて読ませ、統合して 1 本の md にする

件数の閾値は固定値を SKILL.md に書かず、ゲート 1 で人間に判断材料として提示する。

        ├── references/

        │   ├── api.md

        │   ├── integrations.md

        │   └── stacks/            後から足せる差し込み口
        ├── templates/

        │   ├── screens.md

`skills/<skill-name>/SKILL.md` はプラグインの規約。この配置にしたことで、
プラグインとしても、個人スキル（`~/.claude/skills/`）としても、
プロジェクトスキル（`<project>/.claude/skills/`）としても同じ中身が使える。

スクリプトは**このスキルのディレクトリからの相対パス**で呼ぶ。
配置場所が 3 通りあるので、絶対パスを組み立てない。

`notes/` は案件固有の情報を含むため公開しない（`.gitignore`）。

### SKILL.md の責務

書くもの — 起動条件と description、コマンド仕様、00〜05 のワークフローとゲート、各段階で読む `references/` の指定、書かないこと、このスキルの限界。

書かないもの — フレームワーク固有の読み方、資料の章立ての詳細、特定プロジェクトのパスや値。

SKILL.md は常時コンテキストに載る。厚いと実作業の余地が減り、指示そのものが守られにくくなる。

## MVP の線引き

**含む** — コマンド / スタック判定と `references/stacks/` の差し込み口 / 8 資料の生成 / Markdown 出力と HTML 変換 / 4 スクリプト / ゲート 2 か所 / 実装ファイル欄・未確認一覧・コミットハッシュの記録 / 3 プロジェクトでの実行検証

**含まない** — 差分更新 / `feature` モード / 人間の補足編集との共存 / Notion 反映 / 確度の機械的スコアリング / JSON・YAML の中間表現 / md・html 以外の出力形式

### 将来への備え（MVP で満たす前提条件のみ）

- **差分更新** — 各 md の冒頭に生成時点のコミットハッシュを記録する。「実装ファイル」欄がそのまま依存関係になる。将来は `git diff <ハッシュ>..HEAD` と突き合わせて該当セクションだけ再生成する
- **機能詳細設計** — 画面-API-DB 関連表が「画面 → API → Service → DB」の経路をすでに持つ。将来はこの表を入口に、該当行の範囲だけ深く読み直す

## 要件から落としたもの

1. **確度を独立したメタデータとして持つ** — 機械が正しく付けられる保証がない。付けた確度が信用できなければ読み手はどのみち実装を見に行く。「実装ファイル欄 + 未確認の明記」で同じ目的を果たせる
2. **JSON / YAML の中間表現** — 今の要件に対して 1 段余分。差分更新の実装時に md からの読み戻しでは足りないと分かってから入れる
3. **出力形式のプラグイン化** — 形式が 2 つの時点で抽象化すると、3 つ目で作り直す。md を正本に固定すれば変換器を 1 本足すだけで済む
4. **symbol 単位の追跡** — リファクタのたびに資料が壊れる。ファイル単位なら移動に強く、読み手が探すコストもほとんど変わらない
5. **人間の補足編集との共存を MVP で設計** — 順序が逆。生成物が実用に足るかを 3 プロジェクトで確かめ、補足を書きたくなる箇所が分かってから決める

## 配布

1 リポジトリを marketplace 兼 plugin にしてある。利用者の導線は 3 通り。

- **プラグイン** — `/plugin marketplace add <owner>/source-docs` → `/plugin install source-docs@source-docs`。更新は `/plugin marketplace update`
- **個人スキル** — `skills/source-docs/` の中身を `~/.claude/skills/source-docs/` へ。全プロジェクトで使える
- **プロジェクトスキル** — `<project>/.claude/skills/source-docs/` へ。リポジトリに commit すればチーム全員が使える

依存は Python 3 標準ライブラリのみ。追加インストールを利用者に要求しない。

## このスキルの限界

- **漏れゼロは機械で保証できない。** API・画面ルートは確実に列挙できるが、バッチや Webhook は書き方がプロジェクト次第で、独自構造なら取りこぼしうる
- **機械照合は作文しか検出できない。** 「実在しないエンドポイントを書いた」は防げるが、「分岐条件の説明が実装と違う」「書かれていない分岐がある」は検出できない
- **機密検出は誤検知が出る。** 自動で伏せ字にせず、常に人間の判断に回す
- **未検証のスタックでは精度が落ちる。** 汎用手順は動くが、フレームワーク固有の書き方は `references/stacks/` に無ければ読み取れない
