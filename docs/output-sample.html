8. 未確認一覧

資料の末尾に必ず置く。何が分からなかったかを 1 か所で見渡せるようにする。

対象分からなかったこと調べた範囲
public.orders.coupon_codeどこで書き込まれ、どこで参照されるかAPI・バッチ・管理画面を全文検索したが代入箇所なし
public.order_status.refundedこの状態へ遷移する経路同上。返金は外部の決済管理画面で行われている可能性
public.legacy_book_importsテーブルの用途そのもの参照するコードが 1 か所も無い。移行時の残骸と思われるが確証なし
analytics スキーマ全体マテリアライズドビューの定義元 SQL の所在db/analytics/ に 2 本しか無く、DB 上の 3 本目と対応が取れない。手動で作られた可能性
この資料の書式ルール
  • カラム表は 6 列固定。説明欄に単位と業務ルールを書く — 「integer」だけでは円かポイントか分からない
  • マイグレーションと ORM モデルの両方がある場合、マイグレーションを正とする。両方を実装ファイルに挙げる
  • 用途はコードを読んで書く。命名から推測しない。読めなければ用途ごと未確認一覧へ送る
  • Enum は値だけでなく「その値をセットする処理」を併記する。テスト仕様書を書くとき、ここが最も効く
  • スキーマが複数あるなら 2 章を置き、テーブル名は常にスキーマ修飾で書く。 スキーマが public だけのプロジェクトでは 2 章を省き、修飾も付けない — 単一スキーマで public. を全行に付けるのはノイズにしかならない
  • スキーマごとに管理主体を記録する。外部サービスが作るスキーマ、別リポジトリのマイグレーションが作るスキーマ、手動で作られたスキーマは、変更できる範囲が違う
  • スキーマ跨ぎの FK は制約欄に必ずスキーマを含めて書く。単に FK → users.id と書くと、同名テーブルが両スキーマにあるとき読み手が誤る

分割の方針
  • テーブル 15 本以下 → 全テーブルを 1 枚に、カラム付きで描く
  • 16 本以上 → ドメイン単位（注文まわり / 商品まわり / 認証まわり）に分割し、それぞれカラム付きで描く。加えて全体図をリレーションのみで 1 枚置く
  • カラムは PK / FK / UK と、業務上の主要な列に絞る。全カラムを図に入れない — 全量は 4 章のテーブル定義が持っている
  • 中間テーブルも省略せず描く。省略すると多対多の実装が見えなくなる
スキーマが複数あるとき
  • スキーマ単位で図を分けるのが基本。その上で、跨ぎの参照だけを集めた「スキーマ間参照図」を 1 枚置く
  • 1 枚に混ぜる場合は接頭辞を付ける。public のテーブルには付けない（大半が public のため、全部に付けると読みにくい）
  • 外部管理スキーマのテーブルはカラムを主要な列だけに絞る。 こちらで変更できないうえ、外部サービスの都合で増減するため、全量を書くと資料がすぐ古くなる
  • ビュー・マテリアライズドビューは ER 図に入れない。実体の依存関係が読めなくなる。別章で「どのテーブルから作られるか」を表で示す

レンダリング結果

flowchart TD
    BOOKS["書籍一覧 /books"] --> DETAIL["書籍詳細 /books/[id]"]
    DETAIL -->|"カートに入れる"| CART["カート /cart"]
    DETAIL -.->|"未ログイン"| LOGIN["ログイン /login"]
    LOGIN -->|"認証後は元の画面へ戻る"| DETAIL
    CART -->|"注文手続きへ"| CHECKOUT["注文確認 /checkout"]

    CHECKOUT -.->|"在庫不足 OUT_OF_STOCK"| CART

    HISTORY --> ORDERDETAIL["注文詳細 /mypage/orders/[id]"]
図の書き方
  • 画面を主語にする。 API 名をノードにしない — 非エンジニアが読むため
  • ノードには画面名と Route を両方入れる。名前だけだと実装に辿り着けない
  • 矢印のラベルはユーザーの操作。「ボタン押下」ではなく画面上の実際の文言に寄せる
  • エラー・条件付きの遷移は破線にする。正常系の流れが一目で追える
  • 1 枚に詰め込まない。フローが 12 ノードを超えたら「購入フロー」「会員登録フロー」のように分ける
  • ラベルに HTML タグを書かない。 生成 HTML は Mermaid を securityLevel: strict で描画するため、<br/> は改行にならず文字列として出る。画面名と Route は半角スペースで区切る

5. 障害時の挙動

連携先が落ちたときに何が起きるか。コードから読み取れる範囲で書き、読み取れないものは未確認にする。

連携先落ちたときの利用者への影響リトライ復旧の手段
決済サービス注文が確定できない。 500 が返るなし未確認 — pending の注文を回収する仕組みが見当たらない
メール配信影響なし。注文自体は成立する3 回・指数バックオフ3 回とも失敗するとログのみ。再送する仕組みは無い
書誌データ API影響なし。書影とあらすじが空のまま表示される翌日のバッチ自動で復旧する
オブジェクトストレージ書影が表示されない。 画面は壊れず代替画像になるなし—
この資料の書式ルール
  • 方向で章を分ける（送信 / 受信）。 連携先ごとにまとめると、Webhook と API 呼び出しが混ざって障害の切り分けに使えなくなる
  • タイミング・タイムアウト・リトライ・失敗時の挙動を必ず 4 点セットで書く。 「連携している」だけの記述は、障害時に何の役にも立たない
  • 認証情報は環境変数名と所在のみ。 値・トークン・エンドポイントの秘匿部分は書かない。生成後に機密検出を通す
  • Webhook は冪等性の担保方法を必ず書く。重複配信は必ず起きる
  • 設定だけ残っていて呼び出しが無い連携先も一覧に載せて未確認にする。消してよいのか判断できる材料になる

5 資料に共通すること

形式の違いではなく、全資料が守る原則。

  • すべての行に実装ファイルが辿れる。 テーブル定義・エンドポイント詳細・画面一覧のいずれも、実装ファイルの欄を持つ。ファイル単位まで — クラス名や関数名までは追わない
  • 末尾に必ず未確認一覧がある。 分からなかったことを黙って落とさない。「調べた範囲」まで書くので、次に読む人が同じ調査を繰り返さずに済む
  • 推測を事実として書かない。 書く価値があると判断したときだけ、推測と明示して根拠を併記する
  • 単位と業務ルールを説明欄に書く。 型だけでは仕様が伝わらない。「integer」ではなく「税込・送料込の合計、単位は円」
  • 図はすべて Mermaid。 テキストなので差分が見え、Notion もネイティブに描画する
  • 機密は書かない。 環境変数は名前と所在まで。値・トークン・接続文字列は載せず、生成後に機密検出スクリプトを通す
