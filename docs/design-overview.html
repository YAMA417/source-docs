確定事項

質問で確定した前提。以降の設計はすべてこの上に乗る。

スキルの位置
design-doc を置き換える。機能単位 + Notion 反映という旧スキルの構成は引き継がない。
解析方式

01アーキテクチャ

「解析」と「表現」の分離を、レイヤーではなく工程で実現する。

ハイブリッドの分担

  • スクリプトの担当 — ファイル一覧、ルート定義らしき行の抽出、マイグレーション / スキーマファイルの発見、依存関係の読み取り、件数の集計。決定的で、リポジトリが大きくても安い
  • Claude の担当 — 候補が本物の入口か、テーブルが何のために存在するか、画面がどの API を呼ぶか、遷移がどこへ向かうか。これは実装を読まないと分からない

スクリプトが「探すべき場所」を絞り、Claude はそこだけを深く読む。全ファイルを Claude に読ませないことが、大規模リポジトリで破綻しない唯一の条件になる。

ワークフロー

人間が止める場所は 2 か所だけ。旧 design-doc の運用で分かった「早く見せる」を継承する。

各段階で起きること

  • 00 スタック判定 — manifest と設定ファイルから、フロント / バック / ORM / DB / Router / API フレームワークを判定する。該当する参照ファイルが references/stacks/ にあれば読み込む
  • 01 列挙 — inventory.py を走らせ、ルート候補・スキーマ候補・画面候補と、それぞれの件数を出す
  • ゲート 1 — 判定結果と件数を提示する。「API が 140 本ある」と分かった時点で、人間が対象を絞るか分割するかを決められる。判定を外している場合もここで直る
  • 02 / 03 生成 — 資料 1 本ごとに、実装を読んで md を書き、verify.py で識別子の実在を照合する
  • ゲート 2 — 1 本目を人間が読む。見るのは章構成・粒度・読みやすさ。指摘は規則として記録し、以降の資料に効かせる
  • 05 完了報告 — 生成したファイル一覧と、未確認一覧を必ず出す。何が分からなかったかを黙って終わらせない。secrets.py が機密の混入を検出したら、伏せ字にするかを機械で決めず人間に回す

コマンド仕様

位置引数 3 つは順序を覚えられない。省略時の既定値が自然に決まる引数はフラグにする。

/source-docs [target] [--format md|html|both] [--out <dir>] [--repo <path>]

# target 省略 = all / --format 省略 = md / --out 省略 = docs/system
# --repo 省略 = カレントディレクトリ。複数リポは --repo を繰り返す

/source-docs
/source-docs db
/source-docs api --format html
/source-docs --format both --out docs/architecture
/source-docs --repo ./frontend --repo ./backend

target に取れる値は all / overview / db / api / screens / integrations。ER 図とビュー章は db に、画面遷移図と画面-API-DB 関連は screens に含む — 図だけ単独で作り直す用途がないため、別ターゲットにしない。

元案との違い。 /source-docs all md docs/system は 3 つとも位置引数のため、md と docs/system の順序を覚える必要がある。実際にはほぼ毎回同じ値になるので、既定値を持たせて省略できるほうが速い。target だけは毎回変わるので位置引数のままにする。

02ディレクトリ構成

リポジトリの中身と、~/.claude/skills/ へ置く中身を分ける。

design-doc-skill/            リポジトリ（git init して public）
├── README.md
├── LICENSE
├── docs/
│   └── design-overview.html この資料
└── skill/                   ~/.claude/skills/source-docs/ へ置く中身
    ├── SKILL.md             ワークフローとゲート。固有知識は書かない
    ├── references/
    │   ├── detect.md         スタック判定の手順
    │   ├── db.md             DB をどう読むか
    │   ├── api.md            API をどう読むか
    │   ├── screens.md        画面と遷移をどう読むか
    │   ├── integrations.md   外部連携をどう読むか
    │   ├── writing.md        章立て・図・文体・書かないこと
    │   └── stacks/           後から足せる差し込み口
    │       ├── prisma.md
    │       ├── strapi.md
    │       └── expo-router.md
    ├── templates/
    │   ├── overview.md
    │   ├── database.md
    │   ├── api.md
    │   ├── screens.md
    │   └── integrations.md
    └── scripts/

        ├── secrets.py        機密の混入検出
        └── md2html.py        md → 複数ページ HTML

旧 skill/（design-doc 本体）は置き換えのため入れ替える。notes/ は案件固有の情報を含むため、リポジトリには入れない。

03SKILL.md の責務

読ませるのは手順とゲートだけ。知識は参照ファイルへ追い出す。

書くもの

  • 起動条件と description（「設計書を作って」「構造を把握したい」で起動する）
  • コマンドと引数の仕様
  • 00〜05 のワークフローと、ゲートが 2 か所であること
  • 各段階で読むべき references/ の指定
  • 書かないこと（推測、記録のない経緯）と、このスキルの限界

書かないもの

  • フレームワーク固有の読み方。Prisma のスキーマ記法も Strapi の content-types も references/stacks/ の担当
  • 資料の章立ての詳細。templates/ の担当
  • 特定プロジェクトのパスや値

SKILL.md は常時コンテキストに載る。ここが厚いと、実際の作業に使える余地が減り、指示そのものが守られにくくなる。長さの上限を最初から意識して書く。

04supporting files の責務

読み込むタイミングを分けることが、そのままコンテキスト管理になる。

  • references/detect.md — 00 でだけ読む。manifest / 設定ファイルから何を判定するか
  • references/db.md api.md screens.md integrations.md — 該当する資料を書くときだけ読む。取得項目、探し方、判定できないときの扱い
  • references/writing.md — 資料を書く全段階で読む。章立ての原則、Mermaid の使い方、見出しの深さ、「実装ファイル」欄の書式、未確認の書き方
  • references/stacks/*.md — 00 の判定で該当したものだけ読む。ここが唯一の拡張点。新しいフレームワークへの対応は、このディレクトリにファイルを 1 枚足すだけで済む形にする
  • templates/*.md — 資料ごとの章の定義。全プロジェクト共通の正本

05ソース解析方法

定義が存在するものは定義を読む。定義がないものは推定せず、未確認として残す。

DB

優先順位を固定する。マイグレーション / スキーマ定義ファイル > ORM のモデル定義 > 実行時のクエリ。上位が存在するならそれを正とする。

  • 取得: テーブル / カラム / 型 / PK / FK / NULL 可否 / Default / Index / Enum
  • Relation は FK 定義から取る。ORM のリレーション宣言しかない場合はそちらから取り、根拠のファイルを併記する
  • テーブル用途はコードから読む。命名だけで用途を書かない。読めなければ未確認
  • ER 図は Mermaid の erDiagram。テーブル数が多い場合はドメインごとに分割し、全体図は関連のみに絞る

API

  • ルート定義から入り、ハンドラ → サービス → リポジトリと参照を辿る
  • Validation はスキーマ定義（zod / class-validator / DTO など）から取る。無ければハンドラ内の分岐から拾う
  • Status Code は実装に現れるものだけ書く。フレームワーク既定の暗黙値は「既定」と明記する
  • 認証・認可はミドルウェアやデコレータの適用範囲から判定する
  • 関連 DB は、辿った先のリポジトリ層が触るテーブルを記録する

画面

  • ルータ定義（ファイルベースルーティングならディレクトリ構造）から画面を列挙する
  • 遷移は navigate / push / Link / redirect 等の呼び出しから取る。条件付き遷移は条件も記録する
  • 使用 API は、画面から呼ばれる API クライアント層の関数を辿って特定する。ここが画面-API-DB 関連表の接続点になる
  • 画面遷移図は Mermaid の flowchart。画面を主語にする（API 名を主語にしない）。1 枚に詰め込まず、フロー単位で分ける

外部連携

  • HTTP クライアントの生成箇所、SDK の import、Webhook の受け口から、連携先を列挙する
  • 方向で分ける — こちらから呼ぶもの（送信）と、外部から来るもの（受信）。障害の切り分けが方向単位で行われるため
  • 送信はタイミング・タイムアウト・リトライ・失敗時の挙動を 4 点セットで拾う。「連携している」だけの記述は障害時に役に立たない
  • 受信は署名検証の方法と冪等性の担保を拾う。重複配信は必ず起きる
  • 認証情報は環境変数名と読み出し箇所だけ。値は書かない。生成後に secrets.py で検出する
  • 設定だけ残って呼び出しが無い連携先も一覧に載せ、未確認にする。消してよいか判断する材料になる

画面-API-DB 関連

画面解析で得た「画面 → API」と、API 解析で得た「API → テーブル」を突き合わせて 1 枚の表にする。要件にある将来の機能詳細設計は、この表を辿ることで実現できる。

ビュー・マテリアライズドビュー

ER 図には入れず、DB 定義書の独立章で「どのテーブルから作られるか」を表にする。図に混ぜると実体の依存関係が読めなくなるため。更新のタイミングと利用者に見える経路があるかを必ず書く — マテビューは「いつのデータか」が仕様であり、公開画面が直接参照しているなら更新失敗が利用者に見える。

06中間データ構造

持たない。

inventory.py の出力は一時ファイルとして存在するが、これは Claude が「どこを読むか」を決めるための足場であって、資料の生成元ではない。生成が終われば捨ててよい。

Markdown を正本に据えたことで、中間表現が本来担うはずだった役割は次のように吸収される。

  • 形式の追加 — Markdown から変換する。変換器を 1 本足すだけ
  • 根拠の保持 — 資料本文の「実装ファイル」欄が持つ
  • 差分更新の土台 — 資料本文に記録するコミットハッシュと実装ファイル欄が持つ（項目 10）

中間表現を導入するなら、それは「差分更新を実装する段になって、md からの読み戻しでは足りないと分かったとき」でよい。今の時点で作ると、実際に必要な形が分からないまま構造を固定することになる。

07Markdown / HTML 生成方式

Markdown が正本。HTML は変換で作り、内容は必ず一致する。

Markdown

  • 資料ごとに 1 ファイル。--out 配下に overview.md / database.md / api.md / screens.md と、規模が大きい場合の分割ファイル
  • 見出しは ### まで。図は Mermaid。相対パスとファイル名はインラインコード。将来の Notion 変換で書き直しが出ない範囲の制約だけ守る
  • テーブルの列数や表現は読みやすさ優先。Notion のデータベース機能へ寄せる変換は、後日の変換スキルの仕事

HTML

  • md2html.py が index.html と資料ごとのページを生成する。CSS は 1 枚共通
  • Mermaid は CDN の mermaid.js でブラウザ描画する。ファイルを開くだけで図が出る
  • HTML でだけ効く表現（資料間の相互リンク、目次、長い表の横スクロール）は変換器側で付ける

形式を足すときに触るのは scripts/ の変換器と、SKILL.md の --format の記述だけ。解析側は一切変わらない。これが要件にある「解析と表現の分離」の実体になる。

08不明情報・推測情報の扱い

確度をメタデータとして持たず、本文の書式として持つ。

  • 根拠 — 各テーブル / 各エンドポイント / 各画面の行に「実装ファイル」欄を持つ。ファイル単位で足り、symbol 単位までは追わない
  • 判定できなかったもの — 該当欄に「未確認」と書き、資料末尾に未確認一覧の章を置く。何が分からなかったかを 1 か所で見渡せるようにする
  • 推測 — 原則書かない。書く価値があると判断した場合のみ「推測」と明示し、根拠にした箇所を併記する
  • 機械照合 — verify.py が、資料に書いたエンドポイント / テーブル名 / errorType がソースに実在するかを照合する。不一致は 1 回だけ再生成し、2 回目も不一致なら未確認として残して先へ進む

この方式の限界を SKILL.md に明記する。 照合で防げるのは「実在しない識別子を書いた」だけ。「分岐条件の説明が実装と違う」「書かれていない分岐がある」は検出できない。旧 design-doc で同じ限界を経験している。

09大規模リポジトリでのコンテキスト管理

3 段構えで、Claude に読ませる量を絞る。

  1. スクリプトが先に絞る — 全ファイルを読まない。inventory.py が候補を出し、Claude はその周辺だけを開く
  2. 資料ごとに実行を分けられる — target を引数に取る理由がこれ。db だけ、api だけを別セッションで走らせられる
  3. 1 資料の中でも分割する — ゲート 1 で件数が分かるので、API が 100 本を超えるような場合はディレクトリ単位でサブエージェントに分けて読ませ、結果を統合して 1 本の md にする

件数の閾値は固定値を SKILL.md に書かず、ゲート 1 で人間に判断材料として提示する。プロジェクトごとに適正が違うため。

10差分更新への拡張

MVP では仕組みを作らない。前提条件だけ満たしておく。

差分更新に必要なのは 2 つ。どちらも MVP の生成物に含める。

  • 生成時点のコミットハッシュ — 各 md の冒頭に記録する
  • 各セクションが依存する実装ファイル — 項目 08 の「実装ファイル」欄がそのまま依存関係になる

この 2 つがあれば、将来の差分更新は「git diff <記録したハッシュ>..HEAD で変更ファイルを取り、実装ファイル欄と突き合わせ、該当するセクションを持つ資料だけ再生成する」で実装できる。MVP の段階で余分な構造を作る必要はない。

11機能詳細設計への拡張

MVP では作らない。土台になる資料だけ先に作る。

/source-docs feature user-registration が必要とするのは「画面 → API → Service → DB」の追跡。この経路は、MVP で作る画面-API-DB 関連表にそのまま入っている。

将来の実装は、既存の資料を入力にして該当行を抽出し、その範囲だけ深く読み直す形になる。ゼロから解析し直す必要がない。要件に挙がっている 3 つの将来機能のうち、MVP の設計が最も効いてくるのがこの部分。

12MVP の線引き

「3 プロジェクトで 8 資料が生成でき、未確認一覧が出る」ところまで。

MVP に含む

これが動けば完成とする

  • コマンド（target / --format / --out / --repo）
  • スタック判定と references/stacks/ の差し込み口
  • 8 資料の生成（概要 / DB（ビュー章を含む）/ ER 図 / API / 画面一覧 / 画面遷移図 / 画面-API-DB 関連 / 外部連携）
  • Markdown 出力と HTML 変換
  • inventory.py / verify.py / secrets.py / md2html.py
  • ゲート 2 か所
  • 実装ファイル欄・未確認一覧・コミットハッシュの記録
  • 3 プロジェクトでの実行検証

MVP に含まない

前提条件だけ用意し、実装は後

  • 差分更新（項目 10 の 2 つで土台のみ）
  • feature モード（関連表で土台のみ）
  • 人間の補足編集との共存
  • Notion 反映（別スキルとして後日）
  • 確度の機械的なスコアリング
  • JSON / YAML の中間表現
  • md / html 以外の出力形式

過剰設計の指摘

要件のうち、MVP から落とすべきと判断したもの。

  1. 「情報の確度」を独立したメタデータとして持つ 確度 3 値を機械が正しく付けられる保証がない。付けた確度が信用できなければ、読み手はどのみち実装を見に行く。「実装ファイル欄 + 未確認の明記」で同じ目的を果たせる。
  2. JSON / YAML の中間表現 今の要件（7 資料を md と html で出す）に対して、中間層は 1 段余分。差分更新を実装する段で、md からの読み戻しでは足りないと実際に分かってから入れる。
  3. 出力形式のプラグイン化 形式が 2 つの時点で抽象化レイヤーを作ると、3 つ目を足すときに結局作り直す。md を正本に固定しておけば、変換器を 1 本足すだけで済む。
  4. symbol 単位の追跡 クラス・関数・型まで記録すると、リファクタのたびに資料が壊れる。ファイル単位なら移動に強く、読み手が探すコストもほとんど変わらない。
  5. 人間の補足編集との共存を MVP で設計する 順序が逆。まず生成物が実用に足るかを 3 プロジェクトで確かめる。補足を書きたくなる箇所が実際にどこか分かってから、守り方を決める。

この設計が承認されたら、この順で進める。
