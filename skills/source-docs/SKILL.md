# source-docs

対象プロジェクトのソースコードから、**初見の開発者がシステム構造を理解できる資料**を作る。

読み手は、新しく参画した開発者・既存機能を改修する開発者・全体を俯瞰したい開発者。

**最重要要件 — ソースコードから確認できないことを事実として書かない。**
分からなかったことは「未確認」と書き、資料末尾の未確認一覧に「調べた範囲」まで残す。

コードをそのまま並べた資料は不可。情報量を増やすこと自体を目的にせず、
**読み手が構造を掴めること**を優先する。

## コマンド

```
/source-docs [target] [--format md|html|both] [--out <dir>] [--repo <path>]
```

| 引数 | 既定値 | 取りうる値 |
| --- | --- | --- |
| `target` | `all` | `all` / `overview` / `db` / `api` / `screens` / `integrations` |
| `--format` | `md` | `md` / `html` / `both` |
| `--out` | `docs/system` | 任意のディレクトリ |
| `--repo` | カレントディレクトリ | 対象リポジトリ。複数リポは繰り返す |

```
/source-docs db
/source-docs --format both --out docs/architecture
/source-docs --repo ./frontend --repo ./backend
```

**プラグインなら起動名は `/source-docs:source-docs`**、手動で置いたなら `/source-docs`。
どちらでも description による自動起動は同じように効く。

ER 図とビュー章は `db` に、画面遷移図と画面-API-DB 関連は `screens` に含む。

## 生成する資料

| ファイル | 含む資料 |
| --- | --- |
| `overview.md` | システム概要・全体構成図・技術スタック |
| `database.md` | スキーマ一覧・テーブル定義（カラム / Index / 制約 / トリガ一覧）・Enum・**ER 図**・ビュー |
| `api.md` | 共通仕様・エンドポイント一覧・**エンドポイント定義**（基本情報 / リクエスト / レスポンス / ステータスコード） |
| `screens.md` | 画面一覧・**画面遷移図**・**画面項目定義**（表示項目 / 入力項目 / アクション）・画面-API-DB 関連 |

※ `api.md` はエンドポイントが多い場合、機能ごとに分割してよい（`api-orders.md` など）。
**省略はしない。**
| `integrations.md` | 連携先一覧・送信（項目定義つき）・受信（項目定義つき）・認証情報の所在 |

**外部から観測できることは書く。内部での実現方法は書かない。**

| 書く | 書かない |
| --- | --- |
| リクエスト・レスポンスの形（項目・型・必須・制約） | 処理の流れ・呼び出しの順序 |
| ステータスコードと、それが返る条件 | どの関数のどの分岐で判定しているか |
| 画面の表示条件・活性条件・エラー表示・遷移の条件 | 状態管理の仕組み・Component 構成 |
| 宣言された構造（カラム・制約・Index・トリガの存在） | トリガ関数の中身・RLS の内容・GRANT |
| 外部連携で送受信する項目 | タイムアウト・リトライ・冪等性の仕組み |

**「失敗したときにどうなるか」は分けて考える。** 呼び出す側・利用者に見える結果
（409 が返る、エラーが表示される、前の画面へ戻る）は**書く**。
内部でどう復旧するか（再送する、ロールバックする、書き戻す）は**書かない**。

**分量は「全体の構造と内容が理解できる」ところまで。** それを超えて作り込まない。
空のブロックを書かず、同じ形のものは繰り返さず、JSON の例は載せない。
説明は 1 行。詳しい処理内容は将来の `feature` モードの担当で、この資料の役目ではない。

**実装ファイルのパスは書かない。** 例外は `overview.md` の技術スタック判定の根拠のみ
（`package.json` のような manifest の名前。処理を実装したファイルではない）。
求められていない章を足さない。

**API・画面・外部連携の「関連テーブル」欄は残す。** 呼び出す側からは見えないが、
資料どうしをつなぐ索引として要る。CRUD までで、そこで何をするかは書かない。

各資料の章の定義は `templates/` にある。書き方の共通規則は `references/writing.md`。

## スクリプトの実行

**このファイル（SKILL.md）が置かれているディレクトリを基準に呼ぶ。**
以下では `<skill-dir>` と書く。実行時にその実パスへ置き換える。

配置場所は 3 通りある。どこに入っていても、SKILL.md と同じディレクトリの
`scripts/` に 4 本のスクリプトがある。

- プラグイン — `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/skills/source-docs/`
- 個人スキル — `~/.claude/skills/source-docs/`
- プロジェクトスキル — `<project>/.claude/skills/source-docs/`

**利用者の作業ディレクトリからの相対パスで呼ばない。** `python3 <skill-dir>/scripts/inventory.py`
と打つと、対象リポジトリ直下の `scripts/` を探して失敗する。

## 開かないファイル

**このスキルは他人のリポジトリを読む。認証情報が入りうるファイルは開かない。**

| 対象 | 例 |
| --- | --- |
| 環境変数の実ファイル | `.env` / `.env.local` / `.env.production` |
| 鍵そのもの | `*.pem` / `*.key` / `*.p12` / `*.jks` / `id_rsa` |
| 認証情報ファイル | `credentials.json` / `service-account.json` / `.npmrc` / `.netrc` / `terraform.tfvars` |
| ディレクトリごと | `.ssh/` / `.aws/` / `.gnupg/` / `.kube/` / `credentials/` / `secrets/` |

同梱スクリプトは `scripts/_secure.py` の判定でこれらを最初から除外する。
**Read や Grep で自分で開くときも同じ規則を守る。** スクリプトが除外していても、
自分で開いてしまえば意味がない。

例外は `.env.example` / `.env.sample` / `.env.template`。外部連携の変数名を知るために読む。

**ただし、開けば値も見える。** 「読むが値は見ない」は約束であって仕組みではない。
テンプレートに実値が書かれているプロジェクトもある。次を守る。

- 変数名の一覧を得たら**それ以上読まない**
- 値を資料に書かない。`=` の右側は転記しない
- 値らしきものが書かれていたら、その事実を人間に伝える（テンプレートに実値が入っている、
  という指摘自体が有用）

## 00 スタック判定

`references/detect.md` を読む。

```bash
python3 <skill-dir>/scripts/inventory.py --repo <path> [--repo <path>...]
```

フロント / バック / ORM / DB を判定する。**判定結果を鵜呑みにしない。**
「判定できず」が出た区分は manifest を直接開いて確かめる。

`references/stacks/` に該当するファイルがあれば読む。無ければ汎用手順で進む。
**推測でフレームワーク名を書かない。**

## 01 入口とスキーマの列挙

同じ `inventory.py` の出力から、schema / route / screen / integration の候補と件数を得る。

候補は足場であって答えではない。候補に挙がらない場所にも入口はある。
特に外部連携は `.env.example` の変数名から逆に辿ると確実。

## 人間ゲート ①

以下を提示し、**対象範囲を人間に確定してもらう。**

- スタックの判定結果。**判定できなかった区分は必ず伝える**
- 種別ごとの件数
- 件数が多い場合、どう分割して読むかの案

ここで判定の誤りが直る。件数が分かることで、人間が対象を絞る判断もできる。

## 02 1 資料目を生成

**まとめて全資料を生成しない。** 1 本書いて人間に見せ、指摘を型に反映してから次へ進む。
そうしないと同じ指摘を資料の本数ぶん受けることになる。

`target` が `all` なら `database.md` から始める。単独指定ならその資料。

1. 該当する `references/` を読む（`references/db.md` など）
2. `templates/` の該当ファイルと `references/writing.md` に従って書く
3. **実装コードを実際に開いて読む。** 既存 docs の要約で済ませない。docs の数値は古いことがあるので実装値で上書きする
4. 出力先は `--out` 配下

続けて照合と機密検出を**両方**走らせる。片方だけで先へ進まない。

```bash
python3 <skill-dir>/scripts/verify.py --doc <生成した md> --repo <path> [--repo <path>...]
python3 <skill-dir>/scripts/secrets.py --doc <生成した md>
```

- 照合が不一致 → 指摘を材料に**再生成する。リトライは 1 回だけ**
- 2 回目も不一致 → その項目を「未確認」として残し、理由を書いて先へ進む
- **機密を検出 → リトライせず、その場で人間に見せる。** 誤検知（仕様説明中の
  「パスワードリセット」やダミーメール）が出るので、伏せ字にする判断を機械にさせない。
  人間が「誤検知」と言えば進み、「本物」と言えば該当箇所を落として再生成する

## 人間ゲート ②

生成した md のパスと内容を提示する。

人間が見るのは**章構成・粒度・読みやすさ**。内容の正しさを全部検証させるのではない。

- 指摘があった → **その指摘を規則として記録し**、以降の資料に効かせる。文章そのものは保護しない
- 承認された → 03 へ

## 03 残りの資料を生成

02 と同じ手順を、残りの資料に対して繰り返す。ゲート ② で得た規則を適用する。
**照合と機密検出は 1 資料ごとに走らせる。** 最後にまとめて 1 回ではない。

資料の量が多い場合、1 資料の中でも分割して読む。
API が 100 本を超えるような場合は、ディレクトリ単位で読んで統合し、1 本の md にする。

## 04 HTML 変換

`--format` が `html` または `both` のときだけ実行する。

```bash
python3 <skill-dir>/scripts/md2html.py --src <out> --out <out>/html
```

`index.html` と資料ごとのページ、共通 CSS が出る。Mermaid は CDN のスクリプトで
描画される（SRI 付き）。**外部スクリプトを一切読み込みたくない場合は `--no-mermaid`**
を付ける。図は描画されずコードのまま残る。

## 05 完了報告

必ず出すもの。

1. 生成したファイルの一覧
2. **未確認一覧** — 各資料の末尾にあるものを集約して提示する。何が分からなかったかを黙って終わらせない
3. 機密検出の結果 — 02 / 03 で各資料に走らせた結果をまとめて報告する。
   検出が 0 件だったことも明示する。「検査した」と分かる形で残す

## 書かないこと

- 推測で埋めた仕様。書く場合は「推測」と明示し、根拠にした箇所を併記する
- 検討の経緯や却下案のうち、docs にもコードコメントにも記録が無いもの
- 機密。環境変数は**名前と所在まで**。値・トークン・接続文字列・私有 IP・内部ホスト名は書かない
- 資料の外へ何かを送る操作。このスキルはローカルのファイルを読み書きするだけで、
  対象リポジトリの内容を外部へ送信しない
- 「使われていない」「不要」の断定。参照が見つからないことは、存在しないことの証明にならない

## このスキルの限界（人間に伝えるべきこと）

- **漏れゼロは機械で保証できない。** API・画面ルートは確実に列挙できるが、
  バッチや Webhook は書き方がプロジェクト次第で、独自構造なら取りこぼしうる
- **機械照合は作文しか検出できない。** 「実在しないエンドポイントを書いた」は防げるが、
  「分岐条件の説明が実装と違う」「書かれていない分岐がある」は検出できない
- **機密検出は誤検知が出る。** だから自動で伏せ字にせず、常に人間の判断に回す
- **未検証のスタックでは精度が落ちる。** 汎用手順は動くが、フレームワーク固有の書き方は
  `references/stacks/` に無ければ読み取れない

## 未実装

差分更新（Git 差分で変更箇所だけ再生成）と `feature` モード（1 機能を追跡して詳細設計を作る）は
未実装。求められたら「未実装。全体の再生成で対応する」と伝える。**勝手に実装しない。**

前提条件だけは満たしてある。各 md 冒頭のコミットハッシュが差分更新の土台になる。
画面-API-DB 関連表が `feature` の土台になる。

Notion への反映もこのスキルには含まない。md を変換する別スキルの担当。
