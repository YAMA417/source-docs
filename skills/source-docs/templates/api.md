# API 仕様（インターフェース定義書）

生成コミット: `<hash>`

**この資料は「呼び出す側が必要とする情報」を定義する。**
入口・入力・出力・ステータスコードを書く。**中で何をどう処理するかは書かない。**

## 1. 概要

API がどう構成されているかを 3〜5 行で。エンドポイントの本数、認証の方式、
バージョニングの有無、フロントとの関係。

## 2. 共通仕様

全エンドポイントに共通する事項。ここに書けば各定義で繰り返さずに済む。

- **ベース URL とバージョニング**
- **認証** — 方式（Bearer / Cookie / API キー）と、認証が要るエンドポイントの範囲
- **エラー形式** — レスポンスの JSON 構造と errorType の一覧
- **ページング** — クエリパラメータの名前と既定値・上限
- **共通ヘッダー** — リクエスト・レスポンスとも

## 3. エンドポイント一覧

全体を 1 枚で見渡せるようにする。

| Method | Path | 概要 | 認証 | 主な関連テーブル |

系統が複数あるなら（REST / RPC / Webhook など）表を分ける。**全エンドポイントを載せる。**

## 4. エンドポイント定義

エンドポイントごとに 1 見出し。`### POST /api/orders — 注文を確定する` の形。

**簡潔に書く。** 見出しの下に 1〜2 行で何をするかと認証の有無を書き、
続けて以下の 3 つの表を置く。**該当が無いブロックは表ごと省く**（「なし」とだけ書いた
見出しを残さない）。

**リクエスト**

| 区分 | 名前 | 型 | 必須 | 制約 | 説明 |

- 区分は `Path` / `Query` / `Header` / `Body`。**1 つの表にまとめる**
- Body の入れ子は `items[].book_id` のようにドット記法で表す
- **制約はスキーマ定義から取る**（zod / class-validator / DTO / JSON Schema）。
  無ければハンドラ内の分岐から拾う。どちらも無ければ「—」
- Header は共通仕様と異なるものだけ。同じなら行を作らない
- リクエストが何も無いエンドポイントは、この表ごと省いて「リクエストなし」と 1 行書く

**レスポンス（200）**

| フィールド | 型 | 説明 |

- 型定義から起こす。**フィールド構成は実装どおり**
- 入れ子はドット記法。配列は `items[]`
- NULL になりうるものは説明欄に「無ければ null」と書く。列は増やさない
- **JSON の例は載せない。** フィールド表があれば足りる
- 型が動的で読めない場合は「未確認」と書き、読めた範囲だけ書く

**ステータスコード**

| Status | 発生条件 | errorType |

- **実装に現れるものだけ。** フレームワーク既定の暗黙値は「既定」と明記する
- 発生条件は**呼び出す側から見た条件**で書く（「在庫が足りない」「他人の注文を指定した」）。
  実装のどの行で判定しているかは書かない
- 200 だけのエンドポイントも表を置く。**返らないコードを推測で足さない**

**同じ形のエンドポイントはまとめる。** 「`/api/moves` と同じ形。Query は `name` と `q`」
のように 2〜3 行で済ませ、表を繰り返さない。

## 書かないこと

**呼び出す側から見えないものは書かない。**

- 処理の流れ・呼び出しの順序・トランザクションの境界
- 内部で呼ぶ関数・トリガ・ミドルウェアの挙動
- 失敗したときに内部でどう復旧するか
- 実装ファイルのパス
- 呼び出し口を持たない内部関数の定義
