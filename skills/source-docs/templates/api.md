## 1. 概要

API がどう構成されているかを 3〜5 行で。エンドポイントの本数、認証の方式、
バージョニングの有無、フロントとの関係。

## 2. 共通仕様

全エンドポイントに共通する事項。ここに書けば各詳細で繰り返さずに済む。

- **ベース URL とバージョニング**
- **認証** — 方式（Bearer / Cookie / API キー）とミドルウェアの適用範囲
- **エラー形式** — レスポンスの JSON 構造と errorType の一覧
- **ページング** — クエリパラメータの名前と既定値・上限
- **共通ヘッダー**

## 4. エンドポイント詳細

エンドポイントごとに 1 見出し。`### POST /api/orders — 注文を確定する` の形。

冒頭に 2〜4 行で何をするかを書く。トランザクションの境界、部分的な失敗が
起きうるかどうかなど、読み手が最初に知りたいことを先に書く。

続けて 認証 / 認可 / 実装ファイルを並べる。認可は「誰のデータを触れるか」を書く。

そのあとに以下を必要なぶんだけ。

- **Path Parameter** — | 名前 | 型 | 説明 |
- **Query Parameter** — | 名前 | 型 | 必須 | 既定値 | 説明 |
- **Header** — 共通仕様と異なるものだけ
- **Request Body** — | フィールド | 型 | 必須 | 検証 | 説明 |。検証の出所（スキーマ定義のファイル）を表の下に書く
- **Response** — 実際の型定義から起こした JSON。値は例でよいが**フィールド構成は実装どおり**
- **エラー** — | Status | errorType | 発生条件 |
- **関連テーブル** — | テーブル | 操作 | 備考 |。操作は INSERT / UPDATE / DELETE / SELECT

### 守ること

- Validation は**スキーマ定義から取る**。無ければハンドラ内の分岐から拾い、出所を明記する
- Status Code は**実装に現れるものだけ**。フレームワーク既定の暗黙値を書くときは「既定」と明記する
- 関連テーブルは、辿った先のリポジトリ層が触るものを書く。推測で足さない
- 読み取れなかったことは本文に「未確認」と書き、5 章へ送る
