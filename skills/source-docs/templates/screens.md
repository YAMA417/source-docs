# 画面

生成コミット: `<hash>`

**この資料は画面の構成を定義する。** 画面の一覧・遷移・各画面の項目を書く。
**実装の挙動（状態管理の仕組み、Component の構成、内部の分岐）は書かない。**

## 1. 概要

画面がどう構成されているかを 3〜5 行で。ルーティングの方式（ファイルベース /
定義ベース）、画面数、認証が要る範囲。

## 2. 画面一覧

| 画面名 | Route | 概要 | 認証 |

- 画面名は利用者から見た呼び方にする。コンポーネント名をそのまま使わない
- 概要は**1 行**。その画面で何ができるかだけ
- **全画面を載せる。** 一覧から漏れると存在自体が見えなくなる

## 3. 画面遷移図

Mermaid の `flowchart TD`。

- **画面を主語にする。** API 名をノードにしない。非エンジニアが読むため
- ノードには**画面名と Route を両方**入れる。名前だけだと実装に辿り着けない
- 矢印のラベルは**ユーザーの操作**。「ボタン押下」ではなく画面上の実際の文言に寄せる
- **エラー・条件付きの遷移は破線**にする。正常系の流れが一目で追える
- 1 枚に詰め込まない。12 ノードを超えたら「購入フロー」「会員登録フロー」のように分ける
- **ラベルに HTML タグを書かない。** 生成 HTML は Mermaid を `securityLevel: strict` で
  描画するため `<br/>` は改行にならない。画面名と Route は半角スペースで区切る

## 4. 画面項目定義

画面ごとに 1 見出し。`### 注文確認 /checkout` の形。

**簡潔に書く。** 見出しの下に 1〜2 行で何をする画面かと認証の有無、遷移元・遷移先を書き、
続けて以下の 2 つの表を置く。**該当が無いブロックは表ごと省く**（「なし」とだけ書いた
見出しを残さない）。

**画面項目**

| 項目名 | 区分 | 必須 | 制約 / 表示条件 | 取得元 |

- 区分は `表示` / `入力`。**1 つの表にまとめる**
- 項目名は**画面上の文言**。変数名ではない
- 表示項目は**データが入る場所だけ**。静的なラベルは載せない
- 入力項目の制約は**画面側の検証から取る。** API 側と食い違う場合は両方書く
- 取得元は API のエンドポイントかテーブル、または「画面に直書き」。読めなければ「未確認」

**アクション**

| 操作 | 実行できる条件 | 呼ぶ API | 結果 |

- 操作は**画面上のボタン・リンクの文言**
- 実行できる条件は、押せない状態があればその条件。常に押せるなら「—」
- **API を呼ばない操作も載せる。** タブ切替・並べ替え・絞り込み・ダイアログの開閉は
  利用者から見える画面仕様である
- 結果は遷移先の画面名、または画面内で起きること（「一覧が絞り込まれる」）

**表示だけの画面**（静的なページなど）は、表を置かず 2〜3 行の説明で済ませる。

## 5. 画面-API-DB 関連

画面の操作から、呼ばれる API と触られるテーブルまでを 1 行で辿れるようにする。

| 画面 | 操作 / タイミング | API | テーブル（CRUD） |

## 6. 未確認一覧

| 対象 | 分からなかったこと | 調べた範囲 |

## 書かないこと

**利用者から見えないものは書かない。**

- Component の構成、状態管理の仕組み（store / context / hooks）
- 画面内の処理の流れ、非同期処理の順序
- スタイル・レイアウトの実装
- 実装ファイルのパス
