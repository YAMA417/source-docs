# 画面

生成コミット: `<hash>`

## 1. 概要

画面がどう構成されているかを 3〜5 行で。ルーティングの方式（ファイルベース /
定義ベース）、画面数、認証が要る範囲。

## 2. 画面一覧

| 画面名 | Route | 概要 | 認証 | 実装ファイル |

画面名は利用者から見た呼び方にする。コンポーネント名をそのまま使わない。

## 3. 画面遷移図

Mermaid の `flowchart TD`。

- **画面を主語にする。** API 名をノードにしない。非エンジニアが読むため
- ノードには**画面名と Route を両方**入れる。名前だけだと実装に辿り着けない
- 矢印のラベルは**ユーザーの操作**。「ボタン押下」ではなく画面上の実際の文言に寄せる
- **エラー・条件付きの遷移は破線**にする。正常系の流れが一目で追える
- 1 枚に詰め込まない。12 ノードを超えたら「購入フロー」「会員登録フロー」のように分ける
- **ラベルに HTML タグを書かない。** 生成 HTML は Mermaid を `securityLevel: strict` で
  描画するため `<br/>` は改行にならない。画面名と Route は半角スペースで区切る

## 4. 画面詳細

画面ごとに 1 見出し。以下を書く。

- **概要** — その画面で利用者が何をするか
- **遷移元 / 遷移先** — 条件付きなら条件も
- **使用 API** — 呼ぶタイミングと合わせて
- **主要 Component** — 画面固有のものだけ。共通 UI は挙げない
- **実装ファイル**

画面数が多い場合、この章は主要な画面だけに絞ってよい。2 章の一覧は全画面を載せる。

## 5. 画面-API-DB 関連

画面の操作から、呼ばれる API と触られるテーブルまでを 1 行で辿れるようにする。
将来の機能詳細設計はこの表を入口にする。

| 画面 | 操作 / タイミング | API | テーブル（CRUD） |
