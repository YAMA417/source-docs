# DB 定義

生成コミット: `<hash>`

**この資料はテーブルの構造を定義する。** カラム・制約・Index・リレーション、
そして宣言されているトリガやシーケンスの**存在**を書く。
**その中身（トリガが何を検証するか、RLS が誰を通すか）は書かない。**

## 1. 概要

データがどう置かれているかを 3〜5 行で説明する。DB の種類、スキーマの数、
テーブルのおおよその本数。読み手が全体の規模を掴めるようにする。

## 2. スキーマ一覧

**スキーマが `public` だけなら、この章ごと省く。** 単一スキーマで修飾を付けるのはノイズにしかならない。

| スキーマ | 用途 | テーブル数 | 管理主体 / 定義元 |

管理主体は「このリポジトリ」「外部管理（サービス名）」「手動」のいずれか。
外部管理のスキーマはこちらのマイグレーションで変更できないため、必ず区別する。

スキーマ跨ぎの FK があれば、この章で明示する。片方向の依存になるため。

## 3. テーブル一覧

スキーマごとにグループ化する。列は テーブル / 用途。用途は 1 行。

外部管理スキーマのテーブルは「外部管理・定義は読み取りのみ」と添える。

## 4. テーブル定義

テーブルごとに 1 見出し。スキーマが複数あるなら `### public.orders — 注文` の形。

**カラム表**

| カラム | 型 | NULL | Default | 制約 | 説明 |

- 説明欄は**1 行**。**単位と業務ルール**を書く。「integer」だけでは円かポイントか分からない
- 説明欄に処理の流れ・どのファイルが書くか・トリガの挙動を書かない
- 制約欄は PK / FK / UK / CHECK の別と対象を書く。制約が置かれた意図は書かない
- FK はスキーマ修飾で書く（`FK → auth.users.id`）。同名テーブルが両スキーマにあるとき読み手が誤るため
- 用途はコードを読んで書く。命名から推測しない。読めなければ未確認一覧へ送る
- マイグレーションと ORM モデルの両方があるなら**マイグレーションを正**とする

**Index / 制約 / トリガ** — カラム表の下に、**あるものだけ 1 行ずつ**書く。
無いものは行ごと省く。すべて無ければ「Index・トリガとも無し」と 1 行。

```
- Index: `idx_orders_user_created` (user_id, created_at DESC) / `idx_orders_status` (status, where status = 'pending')
- 複合制約: `orders_id_user_id_key` UK (id, user_id) — 子テーブルの複合 FK の参照先
- FK: `user_id` → `auth.users.id`（削除 restrict）
- トリガ: `orders_set_user_id` BEFORE INSERT → `set_user_id()`
```

- Index は名前・対象カラム・部分 Index の条件まで。**何のための Index かは書かない**
  （定義から分かるのはカラムと条件までで、目的はコメントが無ければ推測になる）
- 複合制約は複数カラムにまたがるものだけ。カラム 1 つで完結するものはカラム表の制約欄に書く
- FK は参照先と、更新・削除時の規則
- トリガは**名前・実行時点・事象・呼ぶ関数まで。中身は書かない**

**この 4 種だけ。** RLS・GRANT・参照元・実装ファイルは書かない。

## 5. Enum 定義

| 値 | 意味 |

取りうる値と意味だけ。どの処理がセットするかは書かない。
Enum もスキーマに属するので、定義されたスキーマを見出しに併記する。

## 5-2. シーケンス

**無ければ章ごと省く。** ID の採番方式が `uuid` の生成関数だけなら、カラム表の Default で足りる。

| 名前 | 使うテーブル・カラム | 開始値 | 増分 |

## 6. ER 図

**この章が本体。** Mermaid の `erDiagram`。エンティティ名にドットは使えないので、
スキーマは `auth_users` のような接頭辞で表す。`public` には接頭辞を付けない。

- テーブル 15 本以下 → 1 枚にカラム付きで描く
- 16 本以上 → ドメイン単位に分割し、加えて全体図をリレーションのみで 1 枚
- カラムは PK / FK / UK と業務上の主要な列に絞る。全量は 4 章が持っている
- 中間テーブルも省略しない。省略すると多対多の実装が見えなくなる
- 外部管理スキーマのテーブルはカラムを主要な列だけに絞る。外部の都合で増減するため

## 7. ビュー・マテリアライズドビュー

| 名前 | 種別 | 元テーブル | 更新 | 用途 |

- **更新のタイミングを必ず書く。** マテビューは「いつのデータか」が仕様。抜けると古い数字を見て障害と誤認する
- ビューは ER 図に入れない。実体の依存関係が読めなくなるため
- ビューを参照する API・画面は、それぞれの資料の関連テーブル欄にビュー名で書く。テーブルに読み替えない

## 8. 未確認一覧

| 対象 | 分からなかったこと | 調べた範囲 |

「調べた範囲」まで書く。次に読む人が同じ調査を繰り返さずに済む。

## 書かないこと

以下は俯瞰の邪魔になるうえ、機械照合ができない。**依頼されていない限り書かない。**

- トリガ関数の中身（何を検証するか、何を補完するか）— 存在の一覧までは書く
- RLS ポリシーの内容、列単位の GRANT
- 「どの処理がこの値を書くか」の説明、参照元のファイル
- ストアド関数の内部挙動
- Index が何のために置かれたかの推測
- 実装ファイルのパス
