# detail モードの書き方

1 つの機能を、画面から DB まで追いかけて**どう動いているか**を示す資料の規則。
共通規則は `writing.md`。矛盾したら、機密と推測の禁止を除いてこちらが優先する。

読み手は「その機能を改修する人」。コードを開く前に全体像を掴み、
開いたあとは索引として使う。

## このモードだけが書いてよいこと

他のモードが禁じている次の 2 つを、**このモードは書く**。

- **内部の処理** — 呼び出しの順序、分岐条件、エラー時の復旧、トランザクションの境界
- **実装ファイルのパス** — どこを開けばよいかを示す。これが無いと索引にならない

**それでも書かないもの**は共通規則のまま。機密、推測で埋めた仕様、
「使われていない」の断定は、モードによらず禁止。

## 追跡の手順

入口から順に追う。**途中で分からなくなったら、そこで止めて「未確認」に書く。**
推測でつながない。

1. **入口を特定する** — 画面の操作、API のエンドポイント、Webhook、定期処理のいずれか
2. **呼び出しをたどる** — 入口 → 中間処理 → 永続化。各段でファイルとパスを控える
3. **分岐を洗う** — 正常系を追い切ってから、条件分岐とエラー処理に戻る
4. **DB への影響を確かめる** — どのテーブルに何が起きるか。トランザクションの範囲
5. **外部への送信を確かめる** — 送る項目と、失敗したときの扱い

**全部を追えないことがある。** モノレポやフレームワークの自動処理（ライフサイクルフック、
ミドルウェア）は、呼び出し元が明示されない。追えなかった経路は未確認一覧へ送る。

## 章の構成

`templates/detail.md` に従う。順番を変えない。

1. 概要 — この機能が何をするか（3 行以内）
2. 入口 — 画面・エンドポイント・トリガ
3. シーケンス — 図と、各ステップの説明
4. 分岐とエラー — 条件、そのときの結果
5. データへの影響 — テーブル・カラム・トランザクション
6. 外部連携 — 送受信する項目
7. 関連ファイル — パスの一覧
8. 未確認

## 分量

**1 本 150 行前後。** 250 行を超えたら、追う範囲が広すぎる。機能を分ける。

- 説明は 1 ステップ 1〜2 行
- コードを貼らない。**引用ではなく説明を書く**
- 同じ形の分岐が続くなら「他の 3 件も同じ形」で済ませる

## 図

`sequenceDiagram` を使う。

- 登場するのは 6 者まで。多いなら機能を分ける
- 分岐は `alt` / `else` で表す。破線の矢印は「戻り」に使う
- 外部サービスは参加者名に明示する（`決済サービス` など）
- **図の中に書いたパスは照合されない。** 外部サービスへの呼び出しや概念上のパスを
  書いてよいのはこのため。実在するものは本文の表にも書く

## 関連ファイルの書き方

リポジトリ直下からの相対パスを、インラインコードで書く。

```
| 役割 | パス |
| --- | --- |
| 入口 | `frontend/app/api/articles/route.ts` |
| 保存 | `backend/strapi-app/src/api/article/services/article.ts` |
```

`verify.py --mode detail` がこのパスの実在を確かめる。
**存在しないパスを書くと不一致になる。** ディレクトリだけを書かない。

## 照合

生成したら必ず両方を走らせる。

```bash
python3 <skill-dir>/scripts/verify.py --doc <md> --repo <path> --mode detail
python3 <skill-dir>/scripts/secrets.py --doc <md>
```

照合が見るのは「実在しないものを書いた」誤りだけ。
**分岐条件の説明が実装と違う誤りは検出できない。** そこは人間が読む。
