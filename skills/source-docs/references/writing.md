# 書き方（共通規則）

**全資料・全注釈に共通する規則。** 対象ごとの規則は `structure.md` / `flow.md` / `detail.md`。

## 規則の優先順位

上が強い。下は上を上書きできない。

1. **機密を書かない・推測で埋めない** — どの資料でも、何があっても曲げない
2. この共通規則
3. 対象ごとの規則（`structure.md` / `flow.md` / `detail.md`）
4. `annotations.md` — 書式だけを決める。規則は決めない

「内部の処理を書くか」「実装パスを書くか」は対象で変わる。1 と 2 は変わらない。

## 必ず守ること

- 言語は日本語。注釈の文字列は 1 行で書く（改行を入れない）
- 判定できなかったものは書かずに `unverified` へ送り、**「調べた範囲」（searched）を書く**
- 書いたことには根拠（evidence）を付ける。根拠に挙げるのは実際に開いて読んだファイルだけ
- 機械が書く項目（件数・関係・カラムの型・方向・環境変数名・図）を注釈で書き直さない。
  **機械の結果が誤りだと確かめたら `disputes` に書く。** 本文から外れ「未確定」に移る
- 本文に誤りを残したまま、未確認欄で訂正しない。読み手は本文だけを読んで判断する
- 「バグ」「不具合」と判定しない。今の動きを事実として書き、気を付けることは注意点（`risks`）に分ける

## 書かないこと

- **推測で埋めた仕様。** 書く価値があると判断した場合のみ「推測」と明示し、根拠にした箇所を併記する
- 検討の経緯や却下案のうち、docs にもコードコメントにも記録が無いもの
- **機密。** 環境変数は名前まで。以下は書かない
  - 値・トークン・API キー・パスワード・接続文字列
  - 私有 IP アドレス（`10.` / `192.168.` / `172.16-31.`）と内部ホスト名（`*.internal` `*.local` `*.corp`）
  - 実在する個人のメールアドレス・電話番号
  - 秘匿部分を含む URL（クエリにトークンが乗っているものなど）
- 「使われていない」「不要」の断定。参照が見つからないことは、存在しないことの証明にならない
- HTML タグ。`<br>` などを注釈に書かない（Mermaid は strict で描くので改行にもならない）

## 未確認の書き方

`searched` には、次に読む人が同じ調査を繰り返さずに済むよう、**どこまで探したか**を具体的に書く。

- 良い:「`src/api` と `src/lib` を `timeout` で全文検索。指定箇所なし。SDK の生成は `src/lib/stripe.ts` の 1 か所」
- 悪い:「不明」「コードを見たが分からなかった」

## 日本語の 1 文字を取り違えない

生成中に別の文字（同じ見た目の別字・別言語の文字）が混ざる事故が実際に起きる。
書いたあと、見慣れない文字が無いか確認する。
