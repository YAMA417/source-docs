# 画面の読み方

## 探す場所

| ルーティングの方式 | 探す場所 |
| --- | --- |
| ファイルベース | `app/**/page.tsx` `pages/**` `lib/pages/**` |
| 定義ベース | ルータの定義ファイル（`router.ts` `routes.dart` など） |
| ナビゲーション定義 | Navigator / Stack の構成。URL を持たないことがある |

**URL を持たない画面がある。** モバイルアプリではルートが URL でなく画面名なので、
Route 欄には画面名や定数名を書く。「URL が無い」ことを理由に一覧から落とさない。

## 遷移の辿り方

`navigate` / `push` / `replace` / `Link` / `redirect` / `go` の呼び出しを追う。

- **条件付き遷移は条件も記録する。** 「未ログインならログイン画面へ」は仕様
- 認証ガードによる遷移は、ガードの実装を読んで書く
- エラー時の遷移（在庫不足で戻る、など）も拾う。図では破線にする
- 戻る操作は図に描かない。すべての画面から戻れるため情報にならない

## 使用 API の辿り方

画面 → API クライアント層 → エンドポイント、の順に辿る。
**画面のファイル内に URL が直接書かれていないことが多い。** クライアント層の関数名で辿る。

ここで得た「画面 → API」と、API 資料の「API → テーブル」を突き合わせて
画面-API-DB 関連表を作る。**辿る過程で読んだ画面内部の処理は資料に書かない。**

## 画面項目の取り方

画面項目定義には、**利用者から見えるもの**だけを書く。

- **表示項目** — 画面に出るデータ。JSX / テンプレートの中で変数を描画している箇所から取る。
  項目名は**画面上の文言**。静的なラベルは載せず、データが入る場所だけ
- **入力項目** — フォームの各要素。種別・必須・制約を書く。
  制約は画面側の検証（react-hook-form / zod / HTML 属性）から取る。
  **API 側の制約と食い違う場合は両方書く。** 食い違い自体が情報になる
- **アクション** — ボタン・リンクの文言と、それが呼ぶ API と遷移先

## 取らないもの

Component の構成、状態管理の仕組み（store / context / hooks）、画面内の処理の流れ、
非同期処理の順序、スタイルの実装、実装ファイルのパス。

判断の基準は「**利用者から見えるか**」。見えないものは書かない。

## 図の描き方

- 画面を主語にする。API 名をノードにしない
- ノードに画面名と Route を両方入れる
- 矢印のラベルは画面上の実際の文言に寄せる
- エラー・条件付きの遷移は破線
- 12 ノードを超えたらフロー単位で分ける
- **ラベルに HTML タグを書かない。** 生成 HTML は Mermaid を `securityLevel: strict` で
  描画するため `<br/>` は改行にならない。画面名と Route は半角スペースで区切る

## 判定できないとき

- 遷移先が動的（変数で決まる）→ 「未確認」と書き、読めた候補を列挙する
- 画面が API を呼んでいるように見えない → どこから状態を得ているかを追う。
  追えなければ未確認一覧へ。**「呼んでいない」と断定しない**
