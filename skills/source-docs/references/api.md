# API の読み方

## 辿り方

ルート定義 → ハンドラ → サービス → リポジトリ。この 4 段を辿って初めて
「この API がどのテーブルを触るか」が分かる。ルート定義だけ見て書かない。

## 探す場所

| 形 | 典型的な場所 |
| --- | --- |
| 定義ベース | `routes/` `controllers/` `endpoints/` |
| ファイルベース | `app/**/route.ts` `pages/api/**` |
| デコレータベース | `@Controller` `@Get` などの付いたクラス |
| GraphQL | `resolvers/` `*.graphql` |
| 自動生成 | Strapi のような CMS。`references/stacks/` を見る |

## 取るもの

**呼び出す側が必要とするものを全部取る。**

- **Method / Path** — ルート定義から
- **認証・認可** — ミドルウェアやデコレータの適用範囲から判定する。
  ただし資料には「認証が要る／要らない」と方式だけを書く。**ミドルウェア名は書かない。**
  認可は「誰のデータを触れるか」まで（リクエストの id を使うのか、トークンから取るのか）
- **リクエスト** — Path / Query / Header / Body。フィールド名・型・必須・制約。
  **制約はスキーマ定義から取る**（zod / class-validator / DTO / JSON Schema）。
  無ければハンドラ内の分岐から拾う
- **レスポンス** — 型定義から起こしたフィールド構成
- **ステータスコード** — 実装に現れるものだけ。errorType と発生条件をつける。
  フレームワーク既定の暗黙値は「既定」と明記
- **関連テーブル** — 辿った先のリポジトリ層が触るテーブル。CRUD をつける

リポジトリ層まで辿る理由は関連テーブルを知るため。
**辿る過程で読んだ処理の中身は資料に書かない。**

## 取らないもの

処理の流れ・呼び出しの順序・トランザクションの境界・失敗時に内部でどう復旧するか・
トリガやミドルウェアの挙動・実装ファイルのパス・呼び出し口を持たない内部関数。

判断の基準は「**呼び出す側から見えるか**」。見えないものは IF ではない。

## 発生条件の書き方

ステータスコードの発生条件は**呼び出す側から見た条件**で書く。

- 良い — 「在庫が足りない」「他人の注文 ID を指定した」
- 悪い — 「`checkStock()` が false を返したとき」「トリガ `enforce_limit` が例外を投げる」

## 分量の判断

**一覧表は全エンドポイントを載せる。** 一覧から漏れると存在自体が見えなくなる。
本数が多くても省略せず、系統や機能でグループ化して表を分ける。

**4 章の定義も全エンドポイントに置く。** IF 定義書は各入口の契約が本体なので、
「主要なものだけ」に絞ると資料として成立しない。

本数が多くて 1 ファイルに収まらない場合は、**省略ではなく分割する。**
`api-orders.md` `api-books.md` のように機能で分け、`api.md` に一覧と共通仕様を残して
各ファイルへリンクする。

## 判定できないとき

- ミドルウェアの適用範囲が動的 → 認証欄を「未確認」にする
- 外部から呼ばれる想定か内部専用か分からない → 未確認一覧へ
- レスポンスの型が動的で読めない → 「未確認」と書き、読めた範囲だけ書く
