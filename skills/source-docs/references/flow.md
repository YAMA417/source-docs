# 処理概要（flows）の書き方

1 つの機能について、**何を入れると、何をして、何が出るか**を示す。
読み手は「この機能の仕様を確かめたい人」。実装を読む前の下調べに使う。

## structure・detail との境界

| 資料 | 答える問い | 内部の処理 |
| --- | --- | --- |
| 全体資料 | 何が存在するか | 書かない |
| **処理概要** | 何を入れると何をして何が出るか | **要点だけ（5 行まで）** |
| 詳細設計 | 内部でどう実装されているか | 書く |

**5 行を超えたら、それは detail の領分。** `lint` は 6 行目でエラーにする。

## 書式

```json
"flows": {
  "feature:order-confirm": {
    "summary": "1〜2 文",
    "inputs": [{"name": "productId", "description": "注文する商品"}],
    "steps": ["商品 ID があるか確かめる。無ければ 400 を返す", "Stripe に支払いを作る", "注文を保存する"],
    "outputs": [{"name": "注文", "description": "作った注文"}],
    "failures": [{"condition": "商品 ID が無い", "result": "400 が返る"}],
    "evidence": ["src/app/api/orders/route.ts"],
    "unverified": []
  }
}
```

## steps の書き方

- 1 行 1 ステップ。**動詞で終える。**「注文を作る」「在庫を引き当てる」
- 条件分岐は「〜なら」で 1 行に収める。入れ子にしない
- **関数名・クラス名・ファイル名を書かない。** 何をするかだけを書く（ファイルは「関連」に機械が出す）

書きすぎの例（detail へ回す）: 「`validateOrderInput()` で ZodSchema による検査を行い、失敗時は 422 と field ごとの message を返す」

## failures

利用者・呼び出し側から**見える結果だけ**。内部の復旧（ロールバック・再送）は書かない。

## 図・関連

入力 → 処理 → 出力の図と、画面・API・テーブル・外部連携の関連表は機械が描く。注釈で書かない。
