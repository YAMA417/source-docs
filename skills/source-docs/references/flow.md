# flow モードの書き方

1 つの機能について、**何を入れると何が出るか**を示す資料の規則。
共通規則は `writing.md`。矛盾したら、機密と推測の禁止を除いてこちらが優先する。

読み手は「この機能の仕様を確かめたい人」。実装を読む前の下調べに使う。

## structure との違い

`structure` は「どんな構造か」、`flow` は「何を入れると何が出るか」に答える。
処理の中身には**要点だけ**触れる。手順を追える程度で止め、実装の再現は目指さない。

さらに深く追うのは `detail` の担当。ここで踏み込まない。

## 章の構成

`templates/flow.md` に従う。順番を変えない。

1. 入力 — 利用者・呼び出し側が与えるもの
2. 処理の要点 — **1 行 1 ステップ、5 行以内**
3. 出力 — 返るもの・変わるもの
4. 失敗したとき — 利用者から見える結果だけ
5. 関連 — 画面・API・テーブル・外部連携の名前
6. 未確認

## 処理の要点の書き方

**1 行 1 ステップ。5 行を超えたら、それは `detail` の領分。**

- 動詞で始める。「注文を作る」「在庫を引き当てる」
- 条件分岐は「〜なら」で 1 行に収める。入れ子にしない
- 関数名・クラス名を書かない。何をするかだけを書く
- ファイルのパスは「関連」節にまとめる。本文に散らさない

書いてよい例。

```
1. 受け取った内容を検査する
2. 在庫があれば注文を作る。無ければ 409 を返す
3. 決済サービスへ請求を出す
4. 注文の状態を「確定」にする
```

書きすぎの例（`detail` へ回す）。

```
1. `validateOrderInput()` で ZodSchema による検査を行い、
   失敗時は 422 とともに field ごとの message を返す
```

## 分量

**1 本 40 行前後。** 60 行を超えたら、機能の切り方が大きすぎる。分ける。

- 表は「入力」「出力」「関連」の 3 つまで
- 図は 1 枚だけ。入力 → 処理 → 出力 が 1 目で分かるもの
- JSON の例は載せない

## 図

`flowchart LR` で、左から右に 入力 → 処理 → 出力 を並べる。

- ノードは 8 個まで
- 外部サービスは角を丸めるなどして、自分たちの実装と見分けられるようにする
- シーケンス図は使わない（`detail` の担当）

## 実装ファイルのパス

**「関連」節に書いてよい。** 本文には散らさない。
パスは `verify.py --mode flow` の対象外だが、`detail` を書くときの起点になる。
