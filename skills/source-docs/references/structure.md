# structure モードの書き方

システム全体の構造を示す資料（`overview` / `database` / `api` / `screens` / `integrations`）の規則。
共通規則は `writing.md`。矛盾したら、機密と推測の禁止を除いてこちらが優先する。

## 何を書き、何を書かないか

**外部から観測できることは書く。内部での実現方法は書かない。**

| 書く（外から見える） | 書かない（中の話） |
| --- | --- |
| 入力と出力の形（項目・型・必須・制約） | 処理の順序・呼び出しの流れ |
| ステータスコードと、それが返る条件 | どの関数のどの分岐で判定しているか |
| 画面の表示条件・活性条件・エラー表示 | 状態管理の仕組み・Component 構成 |
| 宣言された構造（カラム・制約・Index・トリガの存在） | トリガ本体の処理・RLS の内容 |
| 遷移の条件（未ログインならログイン画面へ） | 遷移を実装しているガードの中身 |

**「失敗したときにどうなるか」は分けて考える。** 呼び出す側・利用者に見える結果
（409 が返る、エラーが表示される、前の画面へ戻る）は**書く**。
内部でどう復旧するか（再送する、ロールバックする、書き戻す）は**書かない**。

処理の中身を知りたいときは `flow` モード、さらに詳しくは `detail` モードの担当。
このモードで踏み込まない。

## 実装ファイルのパスは書かない

例外は `overview.md` の技術スタック判定の根拠のみ（`package.json` のような manifest の名前。
処理を実装したファイルではない）。

`flow` と `detail` はパスを書いてよい。モードが違えば規則も違う。

## 分量

**目的は「全体の構造と内容が理解できること」。** それを超えた作り込みはしない。

- **空のブロックを書かない。** 「Path Parameter — なし」「Header — 共通のみ」のような
  見出しだけの行を残さず、該当が無ければ**表ごと省く**
- **同じ形のものは繰り返さない。** 「`/api/moves` と同じ形。Query は `name` と `q`」で済ませる
- **例を載せない。** リクエスト / レスポンスの JSON 例は、フィールド表があれば不要
- **表の列を増やさない。** NULL 可否のような情報は説明欄に 1 語で書く
- 説明は**1 行**。2 文以上になったら削る余地がある

**迷ったら書かない。** 書きすぎた資料は読まれず、実装とずれた説明は害になる。
**依頼されていない章を足さない。**

## 図

- 条件付き・エラー系の遷移は破線にして、正常系の流れを追えるようにする
- 画面遷移図・ER 図・全体構成図が対象。シーケンス図はこのモードでは描かない

## 照合を通すための書き方

`verify.py` はテキストの形で識別子を拾う。次を守ると誤検知が減る。

- 表のヘッダーに使う語（「テーブル」など）を、本文のセルで安易に使わない
- テーブル定義の見出しは `### \`public.orders\` — 注文` の形にする
- 関連テーブル欄はテーブル名だけを書き、補足は括弧に入れる

## 関連テーブル欄は残す

**API・画面・外部連携の「関連テーブル」欄は省かない。** 呼び出す側からは見えないが、
資料どうしをつなぐ索引として要る。CRUD までで、そこで何をするかは書かない。
この欄が `flow` と `detail` の土台になる。
