# 全体資料のための注釈

`overview` / `features` / `database` / `api` / `screens` / `integrations` に効く注釈の書き方。
共通規則は `writing.md`。矛盾したら、機密と推測の禁止を除いてこちらが優先する。

## 何を書き、何を書かないか

**外部から観測できることは書く。内部での実現方法は書かない。** 中身は `flow` / `detail` の担当。

| 書く（外から見える） | 書かない（中の話） |
| --- | --- |
| 入力と出力の形（項目・型・必須・制約） | 処理の順序・呼び出しの流れ |
| ステータスコードと、それが返る条件 | どの関数のどの分岐で判定しているか |
| 画面の表示項目・入力項目・操作 | 状態管理の仕組み・Component 構成 |
| カラムの意味・単位 | トリガ本体の処理・RLS の内容 |

**失敗したときに呼び出す側・利用者に見える結果**（409 が返る、エラーが表示される）は書く。
内部でどう復旧するか（再送する、ロールバックする）は書かない。

件数・関係（どの API がどのテーブルを触るか）・カラムの型や制約は**機械が書く。** 注釈で書き直さない。
機械の結果が実装と違うと分かったら、注釈で上書きせず、人間に報告して `unverified` に残す。

## system / applications

- `summary` は README・docs・画面の文言から。**命名から推測しない**
- `users` は画面・認可の実装から分かる範囲（「購入者」「管理者」）。ロールの定義が無ければ未確認

## api（共通仕様）

- **認証・認可** — ミドルウェア・ガード・デコレータの適用範囲を読んで判定する。資料に書くのは方式と範囲だけ。
  ミドルウェア名は書かない。認可は「誰のデータを触れるか」まで（リクエストの id を使うか、トークンから取るか）
- **エラー形式・ページング・ヘッダー** — 共通ハンドラ・API クライアントから。個別の API でしか分からなければ未確認

## endpoint

辿り方は ルート定義 → ハンドラ → サービス → リポジトリ。`show <endpoint ID>` に定義の場所がある。

- **制約はスキーマ定義から取る**（zod / class-validator / DTO / JSON Schema）。無ければハンドラ内の分岐から
- レスポンスは型定義から。型が動的で読めなければ、読めた範囲だけ書いて残りを未確認に
- ステータスは実装に現れるものだけ。**条件は呼び出す側から見た言葉で書く**
  （良い:「在庫が足りない」／悪い:「`checkStock()` が false のとき」）
- **API 仕様を作るときは、全エンドポイントに注釈を付ける。** 1 本ずつ `summary` `auth` `request`
  （無ければ `noRequest: true`）`responses` `errors` を書く。API 仕様は各入口の契約が本体なので、
  一部だけでは資料として成立しない。`lint` は注釈の無い API を警告で数える。**0 件になるまで書く**
- 解析器が入出力を埋めた API（Strapi の既定の API など。`show` の `spec` にある）は、`summary` と `auth` を書けばよい。
  コントローラで上書きしていれば `spec` は無いので、ハンドラを読んで書く
- 認証が全 API で同じなら `api.auth` に書く。個別の `auth` は共通と違うものだけでよい
- コードから確かめられない項目（管理画面の設定で決まる権限など）だけを `unverified` に送り、`searched` を書く

## screen

- `name` は利用者から見た呼び方。コンポーネント名をそのまま使わない
- `displays` はデータが入る場所だけ。静的なラベルは載せない
- `inputs` の制約は画面側の検証（react-hook-form / zod / HTML 属性）から。**API 側と食い違うなら両方書く**
- 遷移は機械が拾う（`router.push` / `Link href` / `redirect`）。条件付き遷移の条件は `actions` の `result` に書く

## table

- `summary` はテーブルの用途を 1 行。**参照するコードを読んで判断する。命名から推測しない**
- `columns` には単位（円かポイントか個数か）と、コードを読まないと分からない意味だけを書く。
  型・NULL・既定値・キーは機械が書く
- 参照が見つからないテーブルも「不要」と書かない。用途を未確認にする

## integration

- **方向（送信 / 受信）・環境変数名・接続先・Webhook の受け口は機械が書く**
- `auth` は方式だけ（「シークレットキーをヘッダーで送る」）。**値・読み出し箇所のパスは書かない**
- `retry` / `timeout` / `failureHandling` は、コードに指定があればその値、無ければ「SDK の既定のまま（指定なし）」と
  根拠つきで書く。SDK の既定値そのものは、コードで確かめられないので書かない
- 設定だけあって呼び出しが無い連携も「使われていない」と書かない

## 図

図は機械が描く（全体構成図・ER 図・画面遷移図・機能ごとの関係図）。注釈で図を書かない。
ER 図と遷移図は 12 ノードを超えると、つながりの塊ごとに分けて描かれる。
