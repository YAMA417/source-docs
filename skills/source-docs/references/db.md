# DB の読み方

## 優先順位

**マイグレーション / スキーマ定義 > ORM のモデル定義 > 実行時のクエリ**

上位が存在するならそれを正とする。値が食い違う場合はマイグレーションを採る。

## 探す場所

| 形 | 典型的な場所 |
| --- | --- |
| SQL マイグレーション | `migrations/` `db/migrations/` `prisma/migrations/` |
| スキーマ定義ファイル | `schema.prisma` `schema.sql` `db/schema.ts`（Drizzle） |
| ORM モデル | `models/` `entities/` `models.py` |
| 独自形式 | `content-types/*/schema.json`（Strapi）など。`references/stacks/` を見る |
| Enum 定義 | スキーマ定義の中、または定数ファイル |

`inventory.py` の `schema` 候補が起点になる。候補に挙がらなかった場所も、
上の表を手がかりに自分で探す。

## 取るもの

テーブル / カラム / 型 / PK / FK / UK / CHECK / NULL 可否 / Default / **Index** /
**テーブル単位の制約** / **トリガの存在**（名前・実行時点・事象・呼ぶ関数）/
**シーケンス** / Enum / Relation。**宣言された構造だけ。**

加えて、**コードを読まないと分からないもの**を 2 つだけ取る。

- **単位** — `integer` が円かポイントか個数か。使っている箇所を読んで判断する
- **テーブルの用途** — 何のために存在するか。1 行。命名から推測しない

## 取らないもの

トリガ関数の中身、RLS の内容、列単位の GRANT、「どの処理がこの値を書くか」、
参照元のファイル、ストアド関数の中身、Index が置かれた目的の推測。

判断の基準は「**宣言されているか、その中で動く処理か**」。
`create index` `create trigger` に書いてあること（名前・対象・時点・事象）は構造なので書く。
トリガ関数の本体が何をするかは処理なので書かない。

## スキーマ

- スキーマが複数あるなら、一覧の章を置き、テーブル名を常にスキーマ修飾で書く
- **単一スキーマなら章も修飾も省く。** 全行に `public.` を付けるのはノイズ
- スキーマごとに管理主体を記録する。外部サービスが作るスキーマはこちらで変更できない
- スキーマ跨ぎの FK は制約欄にスキーマを含めて書く

## ビュー

ER 図に入れず、独立章で「どのテーブルから作られるか」を表にする。
更新のタイミングと、利用者に見える経路があるかを必ず書く。

## 判定できないとき

- テーブルの用途が読めない → 用途ごと未確認一覧へ
- 参照するコードが 1 か所も無いテーブル → 一覧に載せたうえで未確認にする。
  移行時の残骸である可能性が高いが、**確証が無いものを「不要」と書かない**
